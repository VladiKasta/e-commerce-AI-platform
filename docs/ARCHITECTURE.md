# Архитектура проекта

## Общая схема

```text
┌──────────────────────────── Хост-машина ────────────────────────────┐
│                                                                      │
│  Браузер ──► http://localhost:3000 (Nuxt SSR)                        │
│  Браузер ──► http://localhost:9000 (Medusa API + Admin)               │
│                                                                      │
└──────────────────────────────┬───────────────────────────────────────┘
                               │ только опубликованные порты 3000, 9000, 5173
┌──────────────────────────────▼───────────────────────────────────────┐
│                     Docker-сеть ecommerce-starter_ecommerce          │
│                                                                      │
│  ┌──────────┐   ┌─────────┐   ┌──────────────┐   ┌──────────────┐    │
│  │ storefront│──►│  medusa │──►│   postgres   │   │ meilisearch  │    │
│  │  (Nuxt)  │   │ (Medusa)│──►│    redis     │   │  (этап 3)    │    │
│  └──────────┘   └────┬────┘   └──────────────┘   └──────────────┘    │
│                        ▲                                            │
│                 ┌──────┴──────┐                                     │
│                 │    init     │  одноразовый: миграции, seed,       │
│                 │ (одноразовый)│  администратор, publishable key    │
│                 └─────────────┘                                     │
└──────────────────────────────────────────────────────────────────────┘
```

## Ответственность каждого сервиса

| Сервис | Ответственность |
|---|---|
| **postgres** | Единственное хранилище состояния: товары, заказы, клиенты, настройки Medusa. Создает базу и пользователя автоматически при первом старте (механизм официального образа). Не публикуется наружу. |
| **redis** | Сессии Medusa (`redisUrl`), кэш (модуль `cache-redis`), шина событий (`event-bus-redis`) и движок workflows (`workflow-engine-redis`). Данные Redis эphemeral: не критичны и восстанавливаются при рестарте. Не публикуется наружу. |
| **meilisearch** | Поисковый движок каталога (этап 3): индексы товаров/вариантов/цен/остатков/характеристик владеет официальный Search Module Medusa; каталог/поиск/фасеты Store API обслуживаются отсюда. Не публикуется наружу. |
| **init** | Одноразовый процесс инициализации: валидация окружения → миграции (`medusa db:migrate`) → идемпотентный seed → создание администратора. Пишет publishable API key в корневой `.env`. Завершается кодом 0; medusa стартует только после его успешного завершения (`depends_on: service_completed_successfully`). |
| **medusa** | Коммерческий бэкенд: Store API (`/store/*`), Admin API (`/admin/*`), auth (`/auth/*`), health (`/health`) и Medusa Admin (`/app`). Работает в dev-режиме `medusa develop` (hot reload, admin dev-сервер на 5173). |
| **storefront** | SSR-витрина Nuxt с типизированным Commerce Client (`@medusajs/js-sdk`). Серверная сторона (SSR) обращается к Medusa по внутреннему адресу `http://medusa:9000`; после hydration браузер запрашивает публичный URL Medusa напрямую (CORS Store API разрешен). Nitro-маршруты — только `/api/health`. |

## Взаимодействие Nuxt и Medusa

1. **Браузер** запрашивает страницу у Nuxt (`http://localhost:3000`).
2. **SSR (Nitro + Vue на сервере)** рендерит страницу. Данные каталога запрашивает типизированный **Commerce Client** (`useCommerce()` → фасад над официальным `@medusajs/js-sdk`):
   - адресация к Medusa по внутренней Docker-сети: `runtimeConfig.medusaUrl` (`NUXT_MEDUSA_URL=http://medusa:9000`);
   - publishable API key добавляется SDK ко всем запросам автоматически;
   - данные (товары, категории, регионы) попадают в Nuxt payload — после hydration повторных запросов нет.
3. **После hydration** клиентская навигация (пагинация каталога, смена региона) выполняет запросы из браузера **напрямую к публичному URL Medusa** (`runtimeConfig.public.medusaUrl` ← `MEDUSA_PUBLIC_URL`): CORS Store API уже разрешен (`STORE_CORS`), publishable API key публичен по определению.
4. **Nuxt Server API (Nitro)** используется только там, где нужны серверные секреты, cookies или валидация: на этапе 2 это единственный маршрут `/api/health` (health check Docker + статус Medusa). Proxy-маршрут `/api/products` этапа 1 удален — его роль выполняет `useCommerce().products.list()`.

Такая схема выбрана как самая простая (KISS): серверные секреты не попадают в браузер, витрина не дублирует маршруты Medusa собственными proxy, а единственный источник коммерческой логики — Medusa. Детали — в [docs/commerce-client.md](commerce-client.md).

**Разделение приватной и публичной конфигурации** реализовано через `runtimeConfig` Nuxt:

- `runtimeConfig.medusaUrl` — приватная часть (только сервер), значение из `NUXT_MEDUSA_URL`;
- `runtimeConfig.public.{medusaUrl, medusaPublishableKey, medusaTimeoutMs, siteUrl, storeName, storeLocale, storeCurrency}` — публичная часть, значения из `NUXT_PUBLIC_*`.

Publishable API key и публичный URL Medusa — исключения из правила «секретов в браузере нет»: оба публичны по определению (идентификатор канала продаж и публичный адрес API).

**Типизированный Commerce Client (этап 2):**

```text
Vue Components / Pages → Composables (useCommerce, useStore)
    → Commerce Client (shared/utils/commerce-client.ts, фасад над @medusajs/js-sdk)
    → Medusa Store API
```

- Инстанс клиента кэшируется на `nuxtApp`: один на запрос на сервере (нет утечек между пользователями), один на приложение в браузере.
- Ошибки нормализуются в единый `CommerceError` (сеть/таймаут/HTTP/особенности Medusa).
- Региональный контекст (`useStore`) и рассчитанные цены (`region_id` + авто-`fields=+*variants.calculated_price`) инкапсулированы в клиенте и `useStore`.

## Назначение PostgreSQL, Redis и Meilisearch

- **PostgreSQL** — источник истины. Все коммерческие данные создаются только через штатные workflows Medusa (никакой прямой записи в таблицы). Persistent volume `postgres_data` переживает перезапуски.
- **Redis** — транзитное состояние: сессии, кэш, события, оркестрация workflows. Medusa настроена на три штатных Redis-модуля (см. `backend/medusa-config.ts`) — окружение разработки максимально близко к production-конфигурации Medusa. Volume не используется намеренно: потеря этих данных при рестарте не критична.
- **Meilisearch** — поисковая инфраструктура (этап 3): производная проекция каталога. Индексами владеет официальный Search Module Medusa (версии `store_products_vN`, атомарное переключение, seeding, event-ingestion); Medusa/PostgreSQL остается единственным источником достоверных коммерческих данных — окончательные цены и наличие при оформлении всегда читаются из Medusa, не из индекса.

### Выбор активного поискового индекса (этап 3)

Search Module Medusa хранит версии физического индекса (`store_products_v1`, `_v2`, …) и переключает их атомарно; публичного API получения активной версии у модуля нет (модели объявлены внутренней бухгалтерией: `models: []` в joiner-конфиге). Каталог-сервис читает активную версию из `search_index.active_version` той же БД приложения (публичный `PG_CONNECTION` Medusa; TTL-кэш 30 с). **Индекс выбирается исключительно по этому подтверждению**: эвристика максимального номера физической версии исключена — строящаяся версия существует до активации и не должна читаться. При ошибке служебного запроса сервис деградирует к последней подтвержденной ready-версии (ранее атомарно активированной); если подтвержденной версии нет — HTTP 503 `search_unavailable`. Пока новая версия строится, `active_version` указывает на прежнюю ПОЛНУЮ версию — поисковый API никогда не читает незавершенный индекс, а переключение с точки зрения читателей атомарно. Проверено мониторингом во время переиндексации: все запросы до/во время/после swap — HTTP 200 со стабильной выдачей.

### Проверенное поведение Meilisearch 1.58 (прототипы этапа 3)

Выводы технических прототипов, на которые опирается архитектура поиска. Воспроизводятся скриптом `infrastructure/scripts/search-prototype.mjs`; одноразовый пробник wildcard-паттернов `search-patterns.mjs` удален 27.11.2026, его выводы сохранены здесь:

- Родительский объект `attributes` в `filterableAttributes` делает фильтруемыми и фасетируемыми все вложенные поля — новые характеристики не требуют изменений настроек индекса. Работает и альтернатива-wildcard `attributes.*`.
- `distinctAttribute`, заданный на уровне индекса, **влияет** на `facetDistribution` (уточнено 27.11.2026 проверкой на живом индексе `store_products_v3`: у товара с 3 размерами (L/S/M) distribution возвращает `{L:1}`, сумма значений distribution = числу товаров, а не документов — фасеты считаются по множеству ПОСЛЕ дедупликации, «представителям»). Первоначальная формулировка прототипа «не влияет, считает варианты» относилась к пробнику без индексного distinct и неверна для боевого индекса. В обоих случаях distribution не дает точных счетчиков уникальных товаров **по значению** (представитель один на товар, значения остальных вариантов не учитываются) — точные счетчики возможны только отдельными count-запросами (архитектура каталог-сервиса, multi-search).
- Точный `totalHits` при distinct возвращает только page-режим пагинации; limit-режим дает оценочный `estimatedTotalHits`.
- Фильтрация по кириллическим значениям, IN-списки и поиск по вложенным значениям (`searchableAttributes: ["attributes"]`) работают штатно.

## Event-driven Extensibility (сквозное требование V1)

Расширение логики конкретного магазина событиями строится **только на штатных механизмах Medusa v2**; собственная параллельная система событий не разрабатывается:

- **Event Bus на Redis** — используется с этапа 1 (`event-bus-redis`, `medusa-config.ts`); все события системы идут через него.
- **Subscribers** (`src/subscribers`) — подписка на события модулей Medusa и собственных модулей.
- **Workflows и Workflow Hooks** — кастомные бизнес-процессы и предусмотренные hooks штатных workflow без их копирования.

Правила:

1. Кастомная бизнес-логика магазина — отдельные модули, подписчики и точки расширения; ядро Medusa и витрина не изменяются.
2. Собственные модули излучают события изменения данных, если они нужны другим подсистемам. Состав фактически излучаемых событий проверяется на установленной версии Medusa (сейчас 2.23.0): события моделей собственных модулей эмитируются с kebab-case именем объекта (см. [PROGRESS.md](PROGRESS.md), решения №19, №23: `catalog_attributes.product-attribute-value.*`), но несут минимум данных (`data = {id}`) — подписчикам может понадобиться резолвинг затронутых сущностей.
3. Названия событий и доступные Workflow Hooks сверяются с установленной версией Medusa перед использованием.
4. Обработчики идемпотентны; обработка ошибок — штатными средствами (ретраи, компенсации шагов workflow).
5. Перечень фактически поддерживаемых событий (payload, условия возникновения, примеры подписки) и инструкция по добавлению клиентских интеграций без изменения ядра — в `docs/events.md` (создается в рамках V1, см. [ROADMAP.md](ROADMAP.md)).

Универсальный модуль исходящих вебхуков (управление подписками через Medusa Admin, HMAC-подпись, повторная доставка, журнал ошибок, защита от SSRF) — **вне базовой версии**, запланирован в V1.1.

## SEO Content Management (этап 8, V1)

Управление SEO-контентом товаров и категорий (метаполя, H1, SEO-текст) — поверх штатных механизмов Medusa, без отдельной подсистемы контента:

- **Хранение**: существующее поле `metadata` товара/категории, единое типизированное пространство `metadata.seo`. Отдельные таблицы — только при обоснованной необходимости (решение фиксируется в PROGRESS.md). Виджеты изменяют только ключ `seo` — чужие ключи `metadata` не перезаписываются.
- **Medusa Admin**: штатные React-виджеты (Widgets) в карточках товара и категории — блок «SEO и контент»: Meta Title, Meta Description, пользовательский H1, Canonical URL, Robots index/follow, Open Graph, SEO-текст и расположение SEO-текста (до/после основного содержимого). Контент-менеджер не редактирует JSON вручную.
- **SEO-текст**: два формата — обычный текст (переносы строк сохраняются) и HTML (визуальный WYSIWYG-редактор + правка исходного HTML; кандидат — Tiptap React после проверки совместимости с установленной версией Medusa Admin). Обязательные возможности редактора: заголовки, абзацы, форматирование, списки, таблицы, ссылки, изображения.
- **Изображения**: только штатный File Module Medusa (загрузка, alt, подписи, размеры); в `metadata` хранятся только ссылки и атрибуты файлов — Base64 не хранится.
- **Безопасность**: серверная валидация и санитизация HTML до сохранения (белый список тегов/атрибутов, защита от XSS), проверка Canonical URL и загружаемых файлов.
- **Публичный доступ**: доступность `metadata` через штатный Store API проверяется на установленной версии Medusa; при необходимости — минимальное расширение API, возвращающее только разрешенные публичные SEO-поля.
- **Витрина (Nuxt)**: composables `useStoreSeo`, `useProductSeo`, `useCategorySeo`, `useSeoContent` и компонент `SeoContent.vue`; серверный рендеринг SEO-текстов и метатегов — SEO-текст присутствует в исходном HTML ответа без выполнения клиентского JavaScript; адаптивные изображения SEO-блоков; наследование глобальных SEO-шаблонов при отсутствии индивидуальных настроек.

Документация: структура `metadata.seo`, фактические API-маршруты, composables, инструкции для контент-менеджера и разработчика storefront — `docs/seo.md` (состав этапа 8 — в [ROADMAP.md](ROADMAP.md)).

## Принцип управления конфигурацией

1. **Единый корневой `.env`** — единственное место хранения credentials и параметров. В `.gitignore`; в репозитории только шаблон `.env.example` с комментариями.
2. **Генерация при первой установке**: `infrastructure/scripts/generate-secrets.sh` создает отсутствующие секреты (`openssl rand`). Повторные запуски никогда не перезаписывают существующие значения.
3. **Валидация перед запуском**: `infrastructure/scripts/validate-env.mjs` проверяет обязательность, форматы URL, длины секретов. Запускается на хосте (если есть Node) и всегда — внутри init-контейнера перед миграциями.
4. **Каждому контейнеру — только его переменные.** Compose подставляет значения из `.env` в `environment` конкретных сервисов: medusa не получает `ADMIN_PASSWORD`, storefront не получает `JWT_SECRET`/`COOKIE_SECRET` и т.п. (см. `docker-compose.yml`, секция `x-medusa-env`).
5. **Docker Compose нативно валидирует критичные переменные** синтаксисом `${VAR:?сообщение об ошибке}` — запуск с пустым `.env` завершается понятной ошибкой до старта контейнеров.
6. **Publishable API key передается storefront'у** через `.env` (переменная `MEDUSA_PUBLISHABLE_KEY`), куда его записывает seed-скрипт Medusa.

## Принятые архитектурные решения

| Решение | Обоснование |
|---|---|
| **Monorepo pnpm workspace** (`backend/`, `storefront/`) | Один корневой `.env`, один lockfile, общие команды `pnpm -r`. Отсутствие лишних инструментов сборки (turbo) — KISS для двух пакетов. |
| **Dev-режим Docker Compose** (`medusa develop`, `nuxt dev`, bind-mount исходников) | Официально рекомендованный Medusa способ Docker-разработки: hot reload backend и storefront, предсказуемая среда без установки БД на хост. Production-сборка вынесена на этап 10 (YAGNI). |
| **Идемпотентный seed вместо «one-shot»** | `make init` безопасно запускать повторно: нет дубликатов, нет потери данных, seed «дозалечивает» конфигурацию (например, активирует категории). Все данные создаются штатными workflows Medusa. |
| **Init как отдельный compose-сервис** с `service_completed_successfully` | Контролируемая одноразовая инициализация, порядок запуска гарантирован Docker'ом, а не задержками. Простой `docker compose up` самодостаточен: на свежем volume выполнит миграции и seed до старта Medusa. |
| **Health checks для всех сервисов**, readiness через `--wait` и опрос в `status.sh` | Никаких фиксированных задержек: готовность определяется реальными проверками (pg_isready, redis-cli ping, /health). |
| **Prices в основных единицах** | Medusa ≥ 2.20 хранит суммы в major units (1490 = 1490 ₽), что подтверждено официальным линт-правилом `prices-in-major-units`. Витрина форматирует суммы через `Intl.NumberFormat`. |
| **Минимальный типизированный слой витрины** (`shared/types/medusa.ts`) на этапе 1 | Заменен на этапе 2 типизированным Commerce Client поверх официального `@medusajs/js-sdk` (см. [docs/commerce-client.md](commerce-client.md)); в `shared/types/medusa.ts` остались только типы ответов серверных маршрутов Nuxt. |
| **Браузер обращается к Medusa напрямую** (после hydration) | Стандартная схема storefront Medusa: SSR — внутренняя сеть, браузер — публичный URL с CORS. Исключает дублирование маршрутов Medusa собственными proxy. Publishable key и публичный URL не являются секретами. |
| **Анонимные тома `node_modules` + `--renew-anon-volumes`** | pnpm-workspace в bind-mount требует маскировки `node_modules`; флаг гарантирует, что после пересборки образа контейнеры используют актуальные зависимости. |
| **Redis-модули Medusa включены сразу** | Это штатная production-конфигурация Medusa (кэш/события/workflows в Redis), не требует кода и делает dev-среду репрезентативной. |
| **PostgreSQL/Redis/Meilisearch без опубликованных портов** | Требование безопасности: доступ только внутри Docker-сети; проверка извне — через `docker compose exec` (`make status`). |
| **Event-driven Extensibility на штатных механизмах Medusa** (Event Bus Redis, Subscribers, Workflows, Workflow Hooks) | Расширение конкретного магазина — модулями, подписчиками и hooks без изменения ядра Medusa; собственная параллельная система событий не создается. Собственные модули излучают события по необходимости; эмиссия и названия событий/Workflow Hooks сверяются с установленной версией Medusa (2.23.0). Сквозное требование V1, каталог событий — `docs/events.md`; исходящие вебхуки — V1.1. |
| **SEO Content Management в `metadata.seo`** (существующее `metadata` товаров/категорий, штатные React-виджеты Medusa Admin, File Module для изображений, серверная санитизация HTML) | Без отдельной подсистемы контента и отдельных таблиц без обоснованной необходимости; виджет изменяет только ключ `seo` (чужие ключи `metadata` не затрагиваются); контент-менеджер не редактирует JSON; Base64 в `metadata` не хранится; SEO-текст рендерится на сервере без клиентского JavaScript. Этап 8 (V1). |
| **Locking Module с провайдером locking-postgres** (этап 3.6.2) | Штатный провайдер Medusa: advisory-локи в БД приложения работают между процессами и инстансами. Защищает параллельные запуски сверки индекса (job `search-index-reconcile`) и делает межпроцессными seed-локи Search Module (конфликты частичной переиндексации с полной); в мультиинстансном развертывании достаточно общей БД, отдельного сервиса не требуется. |

## Известные компромиссы

- Bind-mount исходников означает, что образы содержат копию кода, которая всегда перекрывается монтированием. Плюс: образ самодостаточен. Минус: пересборка после изменения lockfile — учтено в `make build` / `--renew-anon-volumes`.
- Русскоязычные демо-данные и `pnpm`-специфичные `allowBuilds` в `pnpm-workspace.yaml` привязаны к актуальным версиям инструментов; при их обновлении файлы нужно обновлять.
