## Модель характеристик и хранение в PostgreSQL

Модуль `catalog_attributes` (`backend/src/modules/catalog-attributes/`, миграция `Migration20261126075834`) — 4 таблицы в базе приложения Medusa:

| Таблица | Модель | Назначение | Ключевые колонки |
|---|---|---|---|
| `attribute` | `Attribute` | Реестр характеристик | `code` (уникальный индекс `attribute_code_unique`), `name`, `data_type`, `filter_type`, `unit`, `filterable`, `searchable`, `position`, `option_title` |
| `attribute_option` | `AttributeOption` | Допустимые значения select/multi_select и подписи фасетов | `attribute_id`, `value` (машинное, неизменяемое), `label` (подпись), `position` |
| `category_attribute` | `CategoryAttribute` | Привязки характеристика ↔ категория: какие фильтры показывать в категории каталога и в каком порядке | `attribute_id`, `category_id`, `position` |
| `product_attribute_value` | `ProductAttributeValue` | Значения товаров/вариантов | `attribute_id`, `product_id`, `variant_id` (null = уровень товара), типизированные `text_value` / `numeric_value` / `boolean_value` (заполнена ровно одна); индексы `(product_id, attribute_id)` и `(attribute_id)` |

Принципы хранения:

- **Типизированные колонки значений**: `text`/`select`/`multi_select` → `text_value`; `number` → `numeric_value` (float32); `boolean` → `boolean_value`. Тип проверяется на записи (несовпадение → 400).
- **Ссылки без внешних ключей**: `product_id`/`variant_id` хранят ID без FK — модуль описывает проекцию каталога, не расширяя таблицы Medusa; принадлежность варианта товару проверяется через Product Module на записи (чужой `variant_id` → 400).
- **Soft delete**: все удаления — каскадные soft delete (`deleted_at`): значения товаров → допустимые значения → привязки → характеристика. List-методы, query.graph и витрина видят только живые строки. Физические строки накапливаются с `deleted_at` (очистка не реализована — техдолг в [PROGRESS.md](PROGRESS.md)).
- **PostgreSQL — источник истины**: поисковый индекс — производная проекция; сверка (см. [indexing.md](indexing.md)) восстанавливает соответствие.

Seed демо-данных: 6 характеристик (`brand`, `material`, `color`, `size`, `rating`, `eco`), 51 допустимое значение, привязки к 3 категориям.

## Поддерживаемые типы характеристик

`data_type` — тип хранимого значения (неизменяем после создания — на него ссылается типизированная колонка и ключ индекса `attributes.<code>`):

| `data_type` | Хранение | Фасет в ответе | Пример |
|---|---|---|---|
| `text` | `text_value` | `checkbox`/`select`/`radio`/`color` по `filter_type` | материал |
| `number` | `numeric_value` | `range` (min/max) | `rating` |
| `boolean` | `boolean_value` | `boolean` | `eco` |
| `select` | `text_value` (код из `attribute_option`) | options с подписями из реестра | `brand`, `color` |
| `multi_select` | несколько строк с одним `attribute_id` | options; в документе — массив | `material` |

`filter_type` — способ отображения фильтра витриной (независим от типа данных): `checkbox` (по умолчанию), `select`, `radio`, `range`, `color`, `boolean`. В ответе каталога передается как `facet.type` (для number-характеристик всегда `range`, для boolean — `boolean`).

## Создание характеристик через Medusa Admin

Раздел **«Характеристики»** в навигации Medusa Admin (`http://localhost:9000/app`, UI Route `/app/catalog-attributes`):

1. **Список** — таблица всех характеристик (код, название, тип данных, тип фильтра, число допустимых значений); «Создать» — drawer с формой; серверные ошибки (дубликат `code`) — в toast.
2. **Детальная страница** — редактирование названия, `filter_type`, единицы, позиции, флага «участвует в фильтрации» (`filterable`). `code`/`data_type` неизменяемы (только чтение). Удаление — с подтверждением, каскадное.
3. **Секция «Допустимые значения»** — добавление/изменение подписи/удаление опций `select`/`multi_select` (машиное `value` неизменяемо; удаление опции удаляет ссылающиеся значения товаров).

То же самое доступно через Admin API (маршруты №15–23 [api.md](api.md)) — валидация zod, авторизация Bearer JWT. Пример создания:

```bash
curl -X POST "http://localhost:9000/admin/catalog-attributes" \
  -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \
  --data-raw '{"code":"season","name":"Сезон","data_type":"select","options":[{"value":"summer","label":"Лето"},{"value":"winter","label":"Зима"}]}'
```

Ответ — 201 с объектом `attribute` (включая созданные `options` и пустые `categories`).

## Настройка фильтров и привязка к категориям

Секция **«Категории»** детальной страницы характеристики управляет привязками (маршрут №23 — идемпотентная замена всего набора `category_ids`; порядок массива = `position` в категории):

- **`filterable=false`** — характеристика исчезает из фасетов каталога (значения остаются в поисковых документах и полнотекстовом поиске).
- **Привязки определяют, какие фасеты показывать в категории**: без параметра `category` каталог показывает все `filterable`-характеристики; в категории с привязками — только привязанные, в порядке привязок; **категория без привязок показывает все** (семантика «ничего не выбрано»).
- `unit` и `position` влияют на отображение фасета (единица в `facet.unit`, порядок в массиве `facets`).

Проверено сквозным сценарием (27.11.2026): характеристика без привязок видна в каталоге без категории и скрыта в `?category=t-shirts` (у категории есть другие привязки); после привязки — видна в категории; `filter_type=select` → `facet.type="select"`; `filterable=false` → facet исчезает.

## Назначение характеристик товарам

Виджет **«Характеристики товара»** на карточке товара в Medusa Admin (зона `product.details.after`) либо Admin API (маршруты №24–26):

- **Доступные характеристики вычисляются по категориям товара** с той же семантикой backend: товар без категорий → все; категория без привязок → все; несколько категорий → объединение привязок без дубликатов. **Уже назначенные значения видны и редактируются независимо от категорий** (не удаляются при смене категорий).
- Контролы по типу данных: строка — Input, число — number Input, boolean — Switch, select — Select по допустимым значениям, multi_select — чипы. Единицы отображаются рядом.
- Сохранение — идемпотентная перезапись набора значений пары (характеристика × товар/вариант) (маршрут №25); удаление значений характеристики — per-attribute иконка корзины (маршрут №26).

API-пример (уровень товара; для вариант-специфичного значения добавьте `variant_id`):

```bash
curl -X POST "http://localhost:9000/admin/products/prod_01M87JXH5R6WX9T1HH0G6DG3EA/attribute-values" \
  -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \
  --data-raw '{"values":[{"attribute_id":"attr_01MC...","value":"north-polar"}]}'
```

Ответ — 201 `{ "product_attribute_values": [...] }` (типизированная колонка заполнена, остальные `null`).

**Синхронизация с поисковым индексом** — автоматическая по событиям модуля (`catalog_attributes.product-attribute-value.*`, ~1–2 с), назначенное значение сразу появляется в фасетах каталога (проверено замером, [indexing.md](indexing.md)).

## Отличия характеристик от нативных Product Options

| | Product Options (Medusa) | Характеристики (catalog_attributes) |
|---|---|---|
| Назначение | Оси покупаемого варианта (цвет/размер) — выбор конкретного варианта при покупке | Каталожные фильтры и описательные параметры товара |
| Где задаются | Штатный UI товара Medusa (Options + значения вариантов) | Раздел «Характеристики» + виджет товара |
| Хранение | Таблицы Product Module | Таблицы модуля `catalog_attributes` |
| Вариант-специфичность | Да, по определению | Только при `variant_id` в значении или через `option_title` |
| Фасетный поиск | Нет (штатный `/store/products` не фасетирует) | Да — `filter[code]=...`, счетчики, disjunctive |

**Мост `option_title`**: характеристика со значением `option_title` (например, `color` → «Цвет», `size` → «Размер») не требует ручного ввода для вариантов — значение характеристики **выводится из штатной опции варианта** и попадает только в документы этого варианта (вариант-ориентированная фильтрация). Ручное значение варианта имеет приоритет над опцией. В виджете такие характеристики не показываются — их значения задаются штатным UI опций, без дублирования.

## OR внутри фильтра, AND между фильтрами

Пользовательские фильтры передаются как `filter[code]=v1,v2` (запятая = OR):

- **OR внутри одного кода**: `filter[brand]=deep-sea,urban-basic` → товары любого из брендов (проверено: `total: 6` = 3+3).
- **AND между разными кодами**: `filter[brand]=deep-sea&filter[size]=M` → товар должен удовлетворять обоим.
- **AND с базовыми фильтрами**: `category`, `collection`, `price_min`/`price_max`, `in_stock` всегда комбинируются через AND с атрибутными.
- Неизвестный код → 400 `invalid_query` (валидация против реестра характеристик); значения передаются в Meilisearch только как типизированные строки/числа/булевы — выражения движка из пользовательского ввода не собираются (безопасность фильтров).

Для number/boolean значений одного кода OR собирается ветками `$or` (`attributes.code = 4.5 OR attributes.code = 4.7`); для строк — `$in`-списком.

## Фасетные счетчики

Счетчик значения фасета (`count`) — **точное число уникальных товаров** (не вариантов, не документов):

- проверено: фасет `brand` на всем каталоге — `medusa-originals: 4, deep-sea: 3, urban-basic: 3, north-polar: 2`, сумма = `pagination.total` (12);
- реализация: `facetDistribution` Meilisearch при distinct считает «представителей» дедупликации (по одному документу на товар), поэтому на каждое значение выполняется отдельный count-запрос (`hitsPerPage=0`, точный `totalHits`, все запросы — в одном multi-search вызове); пустая distribution фасета = подтвержденный ноль без count-запросов;
- **disjunctive-семантика**: счетчики значения фасета считаются с учетом всех остальных фильтров, но **без фильтра самого фасета** — пользователь видит, что получит при клике. Выбранные значения остаются в списке (со счетчиком, в т.ч. нулевым) для снятия фильтра;
- до `maxFacetValues: 25` значений на фасет, до `maxFacets: 10` фасетов (порядок — `position` характеристики); подписи значений `select`/`multi_select` — `label` из реестра допустимых значений, у `in_stock` — «В наличии»/«Нет в наличии», у прочих — само значение.

## Диапазоны, сортировка, пагинация

**Диапазоны** (`facet.type="range"`, поля `min`/`max`): фасет `price` (min/max по выборке с учетом остальных фильтров, unit — код валюты региона) и number-характеристики (`rating`, unit из настройки). Бакеты/гистограммы не реализованы. Фильтрация диапазоном: `price_min=1000&price_max=2000` (проверено: `total: 6`; сам фасет price в этом ответе пересчитан disjunctive: min 390 / max 4590).

**Сортировка** (`sort`, в ответе — `sortOptions`): `relevance` (по умолчанию, релевантность Meilisearch), `price_asc`, `price_desc`, `newest` (created_at DESC), `title_asc`. Проверено: `sort=title_asc` → «Бутылка…», «Кружка…», «Лонгслив…», «Свитшот…» (алфавит); `sort=price_asc` → 390, 790, 990 ₽.

**Пагинация** (`limit` 1–100, по умолч 24; `offset` 0–10 000): `pagination.total` — **точное** число уникальных товаров (distinct + page-режим Meilisearch), `hasMore` — наличие следующей страницы. Выдача сгруппирована по товарам: один товар = один `products[]` элемент (вариант-представитель с минимальной ценой в валюте), дубликатов товаров на странице нет.

## Семантика in_stock

`in_stock` в поисковом документе вычисляется **по варианту** (владельцу документа): `manage_inventory=false` **или** `allow_backorder=true` **или** `stocked_quantity − reserved_quantity > 0` (сумма по складам).

Фильтр и фасет `in_stock` в каталоге — по **товарам**:

- `in_stock=true` — есть хотя бы один документ (вариант×валюта) товара в наличии → «товар можно купить»;
- `in_stock=false` — есть хотя бы один отсутствующий вариант → «частично распродан» (НЕ «распродан полностью»). Согласовано со счетчиком фасета: товар с остатком на 1 из 5 вариантов попадает в оба счета (`true: 10`, `false: 4`, total 12 — пересечения допустимы).
- Комбинация с вариант-ориентированными характеристиками: `filter[color]=Чёрный&filter[size]=M&in_stock=true` требует **один вариант** Чёрный × M × в наличии (критический сценарий: total 0, при этом фасет size пересчитан: S: 2, M: 0 selected).

## Примеры подключения фильтров к произвольному storefront

Поисковые маршруты — обычный REST: любой storefront (Nuxt, Next, SPA, мобильный клиент) читает `{products, pagination, facets, sortOptions}` и строит UI фильтров без дополнительного контракта. Заголовок — publishable API key.

**Сценарий 1 — отрисовать фильтры** (один запрос каталога возвращает всё):

```text
GET /store/catalog?category=t-shirts&limit=12
→ facets[]: type=range → слайдер min/max (unit);
  type=boolean/checkbox/select/radio/color → список options
  (label, count, selected) в порядке facet.position
→ products[] → сетка товаров; pagination → пагинатор
```

**Сценарий 2 — применить фильтр** (клик по значению → добавить в URL):

```text
GET /store/catalog?category=t-shirts&filter[brand]=urban-basic&in_stock=true&price_min=500&sort=price_asc
```

Формат `filter[code]=v1,v2` — значения через запятую; несколько значений одного кода = OR. Ссылки фильтров — обычные query-параметры (SSR-friendly, без клиентского состояния); кириллические значения (например, `filter[color]=Чёрный`) кодируются percent-encoding (`%D0%A7...`) — браузеры/SDK делают это автоматически, в raw curl используйте `-G --data-urlencode`.

**Сценарий 3 — снять/переключить фильтр**: `selected: true` у активных значений подсказывает UI, что убрать из URL; disjunctive-счетчики показывают результат клика до клика.

**Сценарий 4 — typeahead**: `GET /store/search/suggestions?q=футб` → до 8 `{text, product_id, handle, sku}`; клик → переход по `handle` на страницу товара (`/store/products?handle=...` для полных данных и рассчитанных цен — не из поискового ответа).

**Сценарий 5 — категория × валютный контекст**: `region_id` (проверка региона на backend, валюта наследуется) определяет валюту фасета price и выдаваемую цену; без региона — регион по умолчанию (валюта магазина).

Композаблы витрины Nuxt (этап 4) построятся поверх тех же маршрутов; типизированные контракты ответов — `backend/src/types/catalog.ts` (зеркало для витрины — `storefront/shared/types/catalog.ts`).
