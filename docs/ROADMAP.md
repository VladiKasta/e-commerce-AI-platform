# Дорожная карта проекта

План развития eCommerce Starter Kit по этапам. Этапы 1–10 — обязательная базовая версия (V1); сквозные обязательные требования базовой версии — в разделе «Сквозные требования V1»; расширения после неё собраны в разделе V1.1. Детали выполнения и текущий статус — в [PROGRESS.md](PROGRESS.md).

## Этап 1. Инфраструктура и базовое развертывание ✅ (завершен)

Docker Compose (PostgreSQL, Redis, Meilisearch, Medusa, Nuxt), единый `.env`, автоматическая инициализация (миграции, идемпотентный seed, администратор, publishable API key), демо-витрина с реальными товарами, базовая документация и API-справочник.

- Демо-страницы: главная, `/catalog` (пагинация), `/product/:handle` (404 для отсутствующего товара) — все на Commerce Client.

- `docs/api.md` (все используемые маршруты Store API), `docs/commerce-client.md`, `docs/composables.md`.

## Этап 8. SEO-подсистема и SEO Content Management, информационные страницы и примеры layout

Обязательная часть базовой версии (V1). Принцип этапа — **Medusa First, Custom Last**: сначала штатные возможности Medusa, собственный код — только для пробелов; результат проверки фиксируется в PROGRESS.md до начала реализации.

Сквозные решения этапа:

- Все SEO-атрибуты хранятся в существующем поле `metadata` товаров, категорий и коллекций в едином типизированном пространстве `metadata.seo`; отдельные таблицы не создаются (только при обоснованной необходимости, решение — в PROGRESS.md); виджеты изменяют только ключ `seo` — чужие ключи `metadata` не перезаписываются.
- Первая задача этапа — аудит штатных возможностей: достаточность `metadata`; доступность `metadata` товаров и категорий через штатный Store API — при необходимости минимальное расширение API, возвращающее только разрешенные публичные SEO-поля.
- Глобальные шаблоны метатегов (генерация title/description из полей сущности) и индивидуальные SEO-настройки с приоритетом над ними; при отсутствии индивидуальных настроек наследуются глобальные шаблоны.

- 8.1 Backend (Medusa): серверная валидация и санитизация SEO-полей — защита от XSS (белый список тегов/атрибутов HTML SEO-текста), проверка Canonical URL и загружаемых файлов; при необходимости — публичное API-расширение из аудита.
- 8.2 Admin Extensions (штатные React-виджеты Medusa Admin): блок «SEO и контент» в карточках товара и категории — Meta Title, Meta Description, пользовательский H1, Canonical URL, Robots (index/follow), Open Graph, SEO-текст и его расположение (до/после основного содержимого); базовые метаполя — также для коллекций. Контент-менеджер не редактирует JSON вручную. SEO-текст в двух форматах: обычный текст (с сохранением переносов строк) и HTML — визуальный WYSIWYG-редактор с возможностью правки исходного HTML; кандидат Tiptap React — после проверки совместимости с установленной версией Medusa Admin; обязательная поддержка заголовков, абзацев, форматирования, списков, таблиц, ссылок и изображений. Изображения — только через штатный File Module Medusa (загрузка, alt, подписи, размеры); Base64 в `metadata` не хранится.
- 8.3 Composables (Nuxt): `useStoreSeo`, `useProductSeo`, `useCategorySeo`, `useSeoContent` — глобальный шаблон, переопределяемый индивидуальными значениями из `metadata.seo`.
- 8.4 Storefront (Nuxt): компонент `SeoContent.vue`; серверный рендеринг SEO-текстов и метатегов — SEO-текст присутствует в исходном HTML ответа без выполнения клиентского JavaScript; адаптивные изображения SEO-блоков.
- 8.5 Инфраструктура SEO: динамические `sitemap.xml` и `robots.txt` (только опубликованные сущности, канонические URL); JSON-LD — Product (Offer), BreadcrumbList, Organization/WebSite; индексация каталога — пагинация и фасетные фильтры без индексируемых дублей (стратегию self-canonical/noindex выбрать при реализации и зафиксировать в PROGRESS.md); базовые 301-редиректы при изменении URL/смене handle (карта редиректов, серверная обработка на Nuxt).
- 8.6 Информационные страницы, примеры layout, документация по переиспользованию.
- 8.7 Обязательная документация: `docs/seo.md` — структура `metadata.seo`, фактические API-маршруты, SEO-composables, инструкция для контент-менеджера (блок «SEO и контент», WYSIWYG-редактор) и разработчика storefront; маршруты — в `docs/api.md`, composables — в `docs/composables.md`.

## Сквозные требования V1

Обязательные требования базовой версии, реализуемые насквозь в рамках этапов 1–10 (не отдельным этапом); полнота проверяется на финальном тестировании (этап 10).

### Event-driven Extensibility

Расширение логики конкретного магазина событиями — только штатные механизмы Medusa v2: Event Bus (Redis), Subscribers, Workflows и Workflow Hooks. Собственная параллельная система событий **не разрабатывается**.

- Кастомная бизнес-логика магазина — отдельные модули, подписчики (`src/subscribers`) и предусмотренные точки расширения Medusa (Workflow Hooks), без изменения ядра Medusa и витрины.
- Собственные модули излучают события изменения данных, если они необходимы другим подсистемам (по образцу штатных событий Medusa); фактический состав эмиссии проверяется на установленной версии — по опыту этапа 3 не все события моделей излучаются автоматически (см. [PROGRESS.md](PROGRESS.md), решение №19).
- Названия событий и доступные Workflow Hooks сверяются с установленной версией Medusa (2.23.0) перед каждой реализацией.

Состав V1:

- Redis Event Bus — штатный `event-bus-redis` (включен с этапа 1).
- Примеры кастомных подписчиков — воспроизводимый шаблон добавления интеграции конкретного магазина.
- Обработка ошибок и идемпотентность обработчиков (штатные средства: ретраи и компенсации workflow-движка, идемпотентные подписчики).
- `docs/events.md`: перечень фактически поддерживаемых событий — payload, условия возникновения, примеры подписки; пополняется этапами по мере появления событий.
- Документация по добавлению клиентских интеграций без изменения ядра (на базе примеров подписчиков и Workflow Hooks).

## V1.1. Расширения после базовой версии

Вне обязательной базовой версии (V1); приоритизируются после этапа 10.

- SEO-посадочные страницы на основе фильтров каталога: индексируемые страницы «категория × значение фильтра» (ЧПУ, уникальные метатеги, JSON-LD ItemList) поверх фасетного поиска этапа 3.
