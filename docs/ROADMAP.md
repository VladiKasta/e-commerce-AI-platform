# Дорожная карта проекта

План развития eCommerce Starter Kit по этапам. Этапы 1–10 — обязательная базовая версия (V1); сквозные обязательные требования базовой версии — в разделе «Сквозные требования V1»; расширения после неё собраны в разделе V1.1. Детали выполнения и текущий статус — в [PROGRESS.md](PROGRESS.md).

Этапы упорядочены по принципу **Backend First, Frontend Last** (перестройка 27.11.2026, см. [PROGRESS.md](PROGRESS.md)): этапы 1–3 — завершенные инфраструктура, Commerce API и поиск; этапы 4–8 — backend (корзина/checkout/заказы, покупатели, платежи/доставка, контент, SEO Content Management и приемка backend); этапы 9–10 — витрина (Commerce Client и composables, страницы и итоговая приемка).

## Этап 1. Инфраструктура и базовое развертывание ✅ (завершен)

Docker Compose (PostgreSQL, Redis, Meilisearch, Medusa, Nuxt), единый `.env`, автоматическая инициализация (миграции, идемпотентный seed, администратор, publishable API key), демо-витрина с реальными товарами, базовая документация и API-справочник.

## Этап 2. Commerce API и базовый типизированный API-клиент ✅ (завершен)

- Типизированный API-клиент storefront на базе официального `@medusajs/js-sdk` (2.23.0): `useCommerce()` c группами `products`, `categories`, `collections`, `regions`.
- Composables: `useCommerce` (транспорт) и `useStore` (регионы, валюта, форматирование цен).
- Региональные рассчитанные цены, пагинация, таймаут, отмена запросов, единая нормализация ошибок `CommerceError`.
- Демо-страницы: главная, `/catalog` (пагинация), `/product/:handle` (404 для отсутствующего товара) — все на Commerce Client.
- Автотесты: unit (31) + интеграционные на живой Medusa (20), `make test`.
- `docs/api.md` (все используемые маршруты Store API), `docs/commerce-client.md`, `docs/composables.md`.

Повторная доставка — штатная идемпотентность модуля + scheduled job `notification-retry` (окно ≈ TTL reset-токена, защита Locking Module); сбой SMTP не ломает штатные сценарии. Mailpit — локальная разработка и тесты (profile compose, UI только `127.0.0.1`, `MAILPIT_ENABLED=false` в production). Документация — [docs/notifications.md](notifications.md); архитектура — решение №39 в [PROGRESS.md](PROGRESS.md); тесты — `store-auth-notifications.spec.ts` (3), `make test` **177/177**. Отдельный сервис рассылок не создавался.
- **Предложение (реализация после V1, отдельным этапом): OTP-подтверждение доступа к гостевому заказу по email.** Текущая модель — possession `x-cart-id` (5.2.1): proof не разглашается случайно, но компрометируется при утечке id корзины (логи, referer, шаринг ссылки). Усиление по штатным механизмам, без отдельной OTP-системы: (а) событийная основа — тот же Notification Module и канал email (провайдер `notification-smtp` уже подключен); (б) код — штатной «полки» для коротких кодов нет, поэтому минимальная таблица модуля-расширения `order_access_codes` (code hash, TTL 10–15 мин, одноразовость, привязка order_id) + подписчик на событие запроса; (в) маршрут-обертка `POST /store/orders/:id/verify` (публикует код на email заказа с серверным rate limiting по образцу 5.2.2) и подтверждение — обмен кода на short-lived possession-cookie; (г) `x-cart-id` продолжает работать параллельно (обратная совместимость витрины). Решение о реализации — на приемке V1; не входит в этап 5.
- **5.3 Интеграционные тесты авторизации и покупателей на живой Medusa** (`make test`): полный цикл регистрация→вход→профиль→адреса→claim корзины→заказ→история; сессии/JWT/refresh/logout; негативные сценарии (дубли email, неверные креды, невалидные токены, 401 без авторизации); изоляция покупателей; разграничение Customer/Admin API; transfer request/cancel; сохранение позиций при claim; изоляция тестовых покупателей и очистка следов прогона. (Часть матрицы уже покрыта 5.2.1 — `store-auth-security.spec.ts` — и 5.2.3 — `store-auth-notifications.spec.ts`.)
- **5.4 Приемка этапа 5:** регрессия `make test`/`make lint`/`make typecheck`, полнота документации (api.md — маршруты 40–53, notifications.md, checkout.md, PROGRESS.md), фиксация побочных эффектов тестов (покупатели/заказы/уведомления не удаляются штатным API).
- **В итоговую приемку backend (этап 8.5) — проверки, зафиксированные этапом 5.2.3:** (1) **TTL rate limiting при отклоненных запросах** — 429 не продлевает блокировку навсегда: окно скользящее, TTL истекает сам (живая проба 5.2.2 на окне 5 с; на приемке — на дефолтных окнах маршрутов аутентификации, включая сброс пароля и transfer); (2) **политика fail-open** — недоступность Redis не должна ломать штатные сценарии (login/reset/transfer отвечают штатными кодами с задержкой ≤~0,5 с/бакет; для уведомлений — недоступность SMTP не меняет HTTP-ответа, повторная доставка ограничена окном); (3) **нагрузка на PostgreSQL** — под нагрузкой контролируются advisory-локи (таблица `locking` пустеет после завершения запросов — нет утечек от middleware 4.5/5.2.1 и job-ов) и подключения к БД (без исчерпания pool-а при пиковых конкурентных checkout/claim/complete).

Исходные требования этапа сохранены: профиль, адреса и история заказов покупателя (`/store/customers/*`, `/store/orders`); **проверка принадлежности заказов покупателю — серверная** (подтверждено аудитом 5.1: `GET /store/orders` фильтруется по auth context); связывание гостевых корзин и заказов штатными механизмами (claim корзины при входе, transfer заказа — проверены аудитом 5.1 и работают).

## Этап 8. SEO Content Management и итоговая приемка backend

Обязательная часть базовой версии (V1). Принцип этапа — **Medusa First, Custom Last**: сначала штатные возможности Medusa, собственный код — только для пробелов; результат проверки фиксируется в PROGRESS.md до начала реализации.

Сквозные решения этапа:

- Все SEO-атрибуты хранятся в существующем поле `metadata` товаров, категорий и коллекций в едином типизированном пространстве `metadata.seo`; отдельные таблицы не создаются (только при обоснованной необходимости, решение — в PROGRESS.md); виджеты изменяют только ключ `seo` — чужие ключи `metadata` не перезаписываются.
- Первая задача этапа — аудит штатных возможностей: достаточность `metadata`; доступность `metadata` товаров и категорий через штатный Store API — при необходимости минимальное расширение API, возвращающее только разрешенные публичные SEO-поля.
- Глобальные шаблоны метатегов (генерация title/description из полей сущности) и индивидуальные SEO-настройки с приоритетом над ними; при отсутствии индивидуальных настроек наследуются глобальные шаблоны.

- 8.1 Backend (Medusa): серверная валидация и санитизация SEO-полей — защита от XSS (белый список тегов/атрибутов HTML SEO-текста), проверка Canonical URL и загружаемых файлов; при необходимости — публичное API-расширение из аудита.
- 8.2 Admin Extensions (штатные React-виджеты Medusa Admin): блок «SEO и контент» в карточках товара и категории — Meta Title, Meta Description, пользовательский H1, Canonical URL, Robots (index/follow), Open Graph, SEO-текст и его расположение (до/после основного содержимого); базовые метаполя — также для коллекций. Контент-менеджер не редактирует JSON вручную. SEO-текст в двух форматах: обычный текст (с сохранением переносов строк) и HTML — визуальный WYSIWYG-редактор (кандидат Tiptap React — после проверки совместимости с установленной версией Medusa Admin) с возможностью правки исходного HTML; обязательная поддержка заголовков, абзацев, форматирования, списков, таблиц, ссылок и изображений. Изображения — только через штатный File Module Medusa (загрузка, alt, подписи, размеры); Base64 в `metadata` не хранится.
- 8.3 Публичные API SEO-полей витрине (из аудита первой задачи этапа); документация маршрутов и пополнение OpenAPI-спецификации (`docs/api.md`, `docs/openapi.yaml`).
- 8.4 Событийная расширяемость: завершение сквозного требования V1 — `docs/events.md` (перечень фактически поддерживаемых событий, payload, условия возникновения, примеры подписки) и примеры кастомных подписчиков.
- 8.5 Интеграционные тесты backend: итоговая регрессия backend-маршрутов этапов 1–8 — на **изолированной тестовой БД** (не dev/production; зафиксировано приемкой 4.4).
- 8.6 Обязательная документация: `docs/seo.md` — структура `metadata.seo`, фактические API-маршруты, инструкция для контент-менеджера (блок «SEO и контент», WYSIWYG-редактор) и разработчика storefront; маршруты — в `docs/api.md`, composables — в `docs/composables.md`.

## Сквозные требования V1

Обязательные требования базовой версии, реализуемые насквозь в рамках этапов 1–10 (не отдельным этапом); полнота проверяется на финальном тестировании (этап 10).

### Event-driven Extensibility

Расширение логики конкретного магазина событиями — только штатные механизмы Medusa v2: Event Bus (Redis), Subscribers, Workflows и Workflow Hooks. Собственная параллельная система событий **не разрабатывается**.

- Кастомная бизнес-логика магазина — отдельные модули, подписчики (`src/subscribers`) и предусмотренные точки расширения Medusa (Workflow Hooks), без изменения ядра Medusa и витрины.
- Собственные модули излучают события изменения данных, если они необходимы другим подсистемам (по образцу штатных событий Medusa); фактический состав эмиссии проверяется на установленной версии — по опыту этапа 3 не все события моделей излучаются автоматически (см. [PROGRESS.md](PROGRESS.md), решение №19).
- Названия событий и доступные Workflow Hooks сверяются с установленной версией Medusa (2.23.0) перед каждой реализацией.

Состав V1:

- Redis Event Bus — штатный `event-bus-redis` (включен с этапа 1).
- Примеры кастомных подписчиков — воспроизводимый шаблон добавления интеграции конкретного магазина.
- Обработка ошибок и идемпотентность обработчиков (штатные средства: ретраи и компенсации workflow-движка, идемпотентные подписчики).
- `docs/events.md`: перечень фактически поддерживаемых событий — payload, условия возникновения, примеры подписки; пополняется этапами по мере появления событий.
- Документация по добавлению клиентских интеграций без изменения ядра (на базе примеров подписчиков и Workflow Hooks).
