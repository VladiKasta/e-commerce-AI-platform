## Принятые архитектурные решения этапа 5

### Решение №39 (зафиксировано ДО реализации 5.2.3): Notification Module и email

Аудит (исходники `@medusajs/notification` 2.23.0 + live-probe 27.11.2026):

1. **Штатный Notification Module** (`@medusajs/medusa/notification`): модели Notification/NotificationProvider (таблица `notification`), публичный контракт `INotificationModuleService` (`createNotifications`, `listNotifications`, `retrieveNotification`), провайдеры по контрактy `AbstractNotificationProviderService` (`send`), каналы (у нас — `email`), штатная идемпотентность `idempotency_key`: повторный вызов `createNotifications` с тем же ключом при SUCCESS — пропуск (дублей нет), при FAILURE — повторная отправка. Встроенные провайдеры: `notification-local` (только логирует; **его лог содержал бы `JSON.stringify(data)` с токеном — отклонен**) и `notification-sendgrid` (SendGrid, не SMTP). **SMTP-провайдера в Medusa нет → реализуется минимальный провайдер `notification-smtp` по штатному контракту** (nodemailer — стандартная библиотека SMTP без транзитивных зависимостей).
2. **Фактические события (live-probe + исходники)**: сброс пароля эмитирует **`auth.password_reset`** (НЕ `auth.password_reset_token_generated` — имя из старых версий Medusa; аудит 5.1 взял его из документации, а не из живой шины; подтверждено probe-подписчиком: payload `{entity_id, actor_type, token, metadata}`, событие эмитится ТОЛЬКО для существующих identity — `createPasswordResetToken` бросает для несуществующих, шаг падает, `emitEventStep` не выполняется). Перенос заказа — `order.transfer_requested`, payload `{id, order_change_id}` — **токен в событии отсутствует**, он в `order_change_action.details.token` (UUID), резолвится через Query API. Ядро эмитит оба события через `emitEventStep` без `attempts` → **штатных ретраев события на шине нет** (1 попытка; падение подписчика = warn в логах).
3. **Собственный сервис рассылок, очередь или Event Bus не создаются**: два тонких подписчика (`backend/src/subscribers/`) вызывают `notificationModuleService.createNotifications` — официальный паттерн Medusa для этих событий (встроенный `configurable-notifications` ядра обслуживает только хардкод `order.created` и к нашим событиям не подключается). Подписчики ошибки НЕ бросают (catch + log, как штатный configurable-notifications) — сбой SMTP не ломает штатные сценарии (201/200 остаются), notification фиксируется как FAILURE.
4. **Повторная доставка** — штатная идемпотентность модуля: минимальный scheduled job `notification-retry` (штатные Scheduled Jobs) подхватывает FAILURE-строки в ограниченном окне (по умолчанию 15 мин ≈ TTL reset-токена; cron `NOTIFICATION_RETRY_CRON`, по умолчанию раз в 5 мин) и повторяет через `createNotifications` с тем же `idempotency_key` — ретраи короткие, ограниченные окном, один получатель; повторная обработка события дублей не создает (idempotency_key: `password-reset:<sha256(token)>`, `order-transfer:<order_change_id>`). Защита от параллельного запуска — Locking Module (прием 3.6.2).
5. **Шаблоны рендерит SMTP-провайдер** (контракт DTO: «template name in the provider's system»): реестр шаблонов в `backend/src/modules/notification-smtp/` (русский язык, HTML + plain text, экранирование пользовательских данных, `encodeURIComponent` токена в ссылках; название магазина из `STORE_NAME`, ссылки из `NUXT_PUBLIC_SITE_URL` без жестко заданного домена; переопределение — правка/добавление модулей шаблонов, без визуального редактора). Получатель определяется только сервером: reset — `entity_id` события (email identity, событие только для существующих), transfer — email заказа (Query API, не инициатор). Контракт ссылок витрины (страницы этапа 9): `/reset-password?token=&email=`, `/account/order-transfer?token=&order_id=`.
6. **Безопасность**: токены не логируются (provider логирует только шаблон/класс ошибки; `notification-local` отклонен именно за логирование data); reset-токен остается одноразовым (штатная генерация/проверка не изменяется); токен в `notification.data` (необходим для отправки) хранится в БД notification — публичные API его не раскрывают (Store API не exposes notifications; Admin API — только администраторам, дублирует то, что ядро и так хранит в `order_change_action`); событие с reset-токеном в Redis transient (штатное поведение ядра, TTL BullMQ-заданий).
7. **Инфраструктура**: Mailpit (docker compose, profile `mailpit`, UI только `127.0.0.1:8025`, SMTP 1025 внутри сети; в production не запускается — `MAILPIT_ENABLED=false`); SMTP-провайдер один и для dev (Mailpit), и для production (реальный SMTP) — замена сервера = правка переменных `.env`, замена провайдера = регистрация другого провайдера в `medusa-config.ts` без изменения подписчиков/шаблонов. Все credentials — в корневом `.env`, в storefront не передаются.

### Находка 5.3 (зафиксирована, НЕ закреплена тестом как ожидаемое поведение)

**Маршруты платежных коллекций не проверяют владельца корзины (upstream Medusa 2.23.0, низкая severity).** Guard 5.2.1 стоит на `/store/carts/:id*`; штатные `POST /store/payment-collections` (тело `{cart_id}`) и `POST /store/payment-collections/:id/payment-sessions` ядром 2.23 не требуют ни авторизации, ни принадлежности корзины. Живая проба (28.11.2026): посторонний покупатель B и анонимный запрос создали payment collection для авторизованной корзины A → 200 с раскрытием суммы корзины (`amount` = total), B добавил payment-сессию → 200; при этом чтение самой корзины B — штатный 404 guard-а. Смягчающие факторы (проверены): cart_id — ULID-секрет, guard не позволяет его узнать (exploit требует утечки id); amount коллекции ядро обновляет при каждом изменении состава корзины (`refreshPaymentCollectionForCartWorkflow` в add/update позиций, промокодах, налогах — недоплаты нет); повторное создание сессии пересоздает ее (delete + create); complete владельца работает без регрессий (probe: 200). Для гостевых корзин поведение соответствует штатной модели Medusa (id = секрет). Влияние: раскрытие суммы чужой авторизованной корзины по известному cart_id и навязывание pre-init состояния платежей. Решение — минимальное расширение guard (проверка владельца cart_id/коллекции на этих маршрутах) **не входит в этап 5.3** (задача — тесты), зафиксировано для приемки backend (8.5) и production-этапа 10; до реализации cart_id обязан храниться серверно (docs/checkout.md — уже требование).

### Технический долг, зафиксированный этапом 5.3 для приемки backend (8.5)

1. **Хранение и срок удаления чувствительных `notification.data`** — reset-/transfer-токены лежат в таблице `notification` (PostgreSQL) весь срок жизни строки; одноразовость/15-мин TTL проверяются на использовании, но строки с токенами не удаляются; Admin API показывает `data`. Оценить: retention/зачистку `data` после доставки, доступ Admin API.
2. **Безопасность ссылок с reset/transfer-токенами** — контракт 5.2.3 кладет токен в query string страниц витрины (`/reset-password?token=…`, `/account/order-transfer?token=…`): токены попадают в логи/историю браузера/referer. При этапах 9–10 рассмотреть однократный обмен токена на серверной сессии (без токена в URL) или подтверждение POST-ом.
3. **Конкурентная работа notification retry job** — параллельный запуск исключен Locking Module (3.6.2), но внутри модуля остается известный TODO ядра (два чтения `failure` → две отправки); при приемке 8.5 проверить под нагрузкой.
4. **Повторная отправка письма при сбое между SMTP-доставкой и сохранением статуса** — SMTP доставил письмо, но `createNotifications` упал до записи `success` → строка `failure` → retry повторит отправку (дубль письма); штатного outbox-а у nodemailer нет. Оценить дедупликацию/требуемость при приемке 8.5.
5. **Изолированное тестовое окружение** — уже зафиксировано приемкой 4.4 (8.5 работает на изолированной БД); туда же: тесты auth не должны зависеть от `jwtExpiresIn` живого окружения (просроченный JWT станет проверяемым конфигурацией).
6. **Независимость тестов от порядка запуска** — для auth-файлов гарантирована `sortTestsFiles` (notifications → … → ratelimit последним) и бюджетом IP-бакетов (≤ 20/30); остаточное ограничение — `store-auth-ratelimit` не рассчитан на 3+ полных прогона в течение минуты (сознательное исчерпание IP-бакетов, задокументировано в спеке) — полностью уходит с изолированным тестовым окружением/своими лимитами в env.

После фикса: A=completed, B=skipped, тест детерминированно проходит. ## Принятые решения этапа 3 (продолжение журнала)

11. **Официальный Search Module Medusa 2.23** вместо собственного Catalog Indexer: индексация/версионирование/ingestion/seeding — штатные механизмы; собственный код — только провайдер и определение индекса. Выбор соответствует правилу №1 AGENTS.md.
12. **Документ = вариант × валюта + distinct** — единственная модель, одновременно дающая вариант-совместную фильтрацию (критический сценарий) и точную пагинацию (прототип, 37/37).
13. **Точные счетчики уникальных товаров**: facetDistribution Meilisearch считает варианты → per-value count-запросы (multi-search, hitsPerPage=0, page-режим с точным totalHits).
14. **Динамические характеристики** фильтруются через родительский объект `attributes` в filterableAttributes Meilisearch (проверено прототипом): новые характеристики работают без изменения настроек индекса. Маршруты валидируют коды фильтров по реестру характеристик; валидатор полей Search Module для динамических путей не используется (обход задокументирован).
15. **В v2 сервисы создаются только в модулях** (официальная документация): `src/services` приложения не регистрируются. CatalogSearchService инстанцируется маршрутами напрямую с request scope.
16. **Доступ к Meilisearch из каталога** — через публичный конструктор собственного провайдера; активная версия индекса — из `search_index.active_version` официального Search Module (через публичный `PG_CONNECTION` Medusa). Публичного API активной версии у Search Module не существует — модели объявлены внутренней бухгалтерией модуля (`models: []` в joiner-конфиге). 20. **Оптимизация фасетного поиска (27.11.2026, эмпирически)**: facetDistribution Meilisearch при distinct считает **представителей** distinct-дедупликации (по одному документу на товар: у худи с 5 размерами distribution = {L:1}; точный count-запрос size=S дает 6 товаров против 2 в distribution) — счетчики distribution не являются ни вариантами, ни точными счетчиками уникальных товаров, поэтому per-value count-запросы сохранены. Из этого следуют два правила оптимизации: (а) для фасета без активного собственного фильтра disjunctive-режим совпадает с базовым запросом → distribution/stats запрашиваются в базовом запросе, отдельный подзапрос — только активным фасетам; (б) **пустая** distribution (Meilisearch возвращает `{}`) = подтвержденный ноль для всех значений фасета → count-запросы не нужны (в модели данных этой задачи значения фасета присутствуют на всех документах товара с этой опцией, поэтому пустая distribution означает отсутствие значений у всех подходящих документов); отсутствие значения в **непустой** distribution нулем не является (maxValuesPerFacet=100). 24. **Сверка индекса — только штатные механизмы Medusa 2.23 (этап 3.6.2, проверено фактом 27.11.2026)**. Аудит Search Module показал готовые механизмы: (а) `reindex({index, filters})` — официальная частичная переиндексация «in-place» в активную версию, никогда не swap-ит, берет lock `search:seed:*`, передает `filters` в seed определения (наш seed поддерживал `product_ids` с этапа 3.2); (б) `deleteDocuments({index, filters})` с быстрым путем удаления по первичному ключу `{id: [...]}`; (в) Scheduled Jobs (workflow engine, BullMQ repeatable с `concurrency: "forbid"`); (г) Locking Module с официальным провайдером `locking-postgres` (advisory-локи в БД приложения, работают между процессами/инстансами). Сверка (`backend/src/jobs/search-index-reconcile.ts`) только композирует их: ожидаемые документы собирают экспортированные загрузчики того же определения индекса, ремонт — через официальный API модуля; чтение сырых документов — метод `fetchDocuments` клиента провайдера (POST documents/fetch, без distinct-дедупликации). Мастер-ключ для чтения: Meilisearch иммутабелен в `actions` существующих API-ключей (PATCH /keys принимает только description/name — эмпирически поймано в первой попытке, из-за чего boot-seeding падал до отката), право documents.get нельзя добавить провижинированным ключам без пересоздания значения — чтение идет master key-ом, серверная внутренняя операция. Каноническое сравнение документов сортирует ключи объектов и элементы массивов: массивы документа (category_ids, значения характеристик) Meilisearch трактует как множества, порядок не входит в контракт и не должен порождать ложные «устаревшие» документы и холостые переиндексации. Дефолтный in-memory Locking Module не защищает между процессами (выявлено живым тестом параллельного запуска) — зарегистрирован locking-postgres, что заодно сделало межпроцессными seed-локи Search Module (защита reindex↔полная переиндексация `make search-reindex` из exec-процесса). Расписание по умолчанию раз в час — сверка дешевая (батчи, только чтения), полная переиндексация по расписанию не выполняется; частота настраивается `SEARCH_RECONCILE_CRON` без изменения кода.
25. **Реентерабельность Locking Module по ownerId (найдено тестами этапа 3.6.3, 27.11.2026)**. Провайдеры Locking Module (in-memory и locking-postgres) считают запрос с ownerId, совпадающим с владельцем удерживаемого lock-а, реентерабельным и пропускают его acquire без конфликта (advisory-lock: `row.owner_id !== ownerId` — единственная проверка). Константный ownerId в `executeSearchReconcile` («search-reconcile-job») пускал параллельные запуски сверки одного владельца мимо lock-а — два одновременных POST /admin/search/reconcile выполняли полный ремонт оба. Исправлено уникальным per-run ownerId (`search-reconcile-<uuid>`) — это же штатная рекомендация документации Locking Module («acquire the lock with an owner that is unique to this call», иначе release может снять чужой lock). Вывод для всех будущих использованием locking в проекте: ownerId — идентификатор ВЫЗОВА, а не сервиса. Защита scheduled job от наложения не зависела от дефекта (BullMQ `concurrency: "forbid"`), ремонт идемпотентен — фактических повреждений дефект не создавал, только лишние параллельные исполнения.

35. **4.5: серверная сериализация завершения корзины — транзакционный advisory-лок через штатный middleware (27.11.2026)**. Дефект из решения №34(а) закрыт на уровне backend. Выбор механизма (по аудиту исходников 2.23.0): (а) внутренние `acquireLockStep`/`releaseLockStep` `completeCartWorkflow` не закрывают гонку — релиз внутреннего лока исполняется шагом workflow ДО коммита транзакции, и конкурент читает «заказа нет» до видимости заказа; (б) Workflow Hooks бесполезны для сериализации (исполняются внутри транзакции); (в) `acquire`/`release` Locking Module непригодны для обертки HTTP-запроса: у провайдера locking-postgres истекшая строка `locking` не передается другому владельцу — упавший процесс навсегда заблокировал бы корзину; (г) выбран **метод `execute` Locking Module** — транзакционный advisory-лок `pg_advisory_xact_lock` через провайдер locking-postgres (зарегистрирован с этапа 3.6.2): PostgreSQL сам снимает лок при коммите, откате и смерти соединения/процесса — гарантированное освобождение без «зависших» строк; владелец лока — сессия БД запроса, идентификация уникальна на каждый запуск по построению (требование «уникальный ownerId» выполняется механизмом провайдера — ownerId-механика acquire/release неприменима к транзакционным локам и не нужна). Точка расширения — штатный middleware-контракт `defineMiddlewares` на пути ядра `/store/carts/:id/complete` (загрузчик регистрирует его перед обработчиком маршрута): защиту нельзя обойти прямым вызовом Store API. Ключ `complete-cart-request:<cart_id>` не пересекается с внутренним ключом workflow (id корзины) — без взаимных блокировок; лок держится до `res finish` (после коммита workflow и ответа), а не до `close` (раннее освобождение переоткрыло бы гонку при обрыве клиента). Ожидание лока до 30 с (стек параллельных повторов) → 409 CONFLICT контрактом ядра. Дубликатов больше нет (probe дважды: один order_id, count=1), последовательные/одновременные повторы идемпотентны штатным `when("create-order")`, разные корзины параллельны, регрессия 157/157. Отложенный остаток: если обработчик запроса никогда не ответит (зависший workflow), лок живет с запросом — это же означает и зависший HTTP-запрос; отдельного таймаута на job в `execute` у 2.23.0 нет, поведение задокументировано.

38. **5.2.2 (решение до реализации): распределенный rate limiting на штатных модулях Cache (Redis) + Locking (PostgreSQL), fail-open; IP — по сокету, без доверия X-Forwarded-For по умолчанию (27.11.2026)**. Аудит механизмов: в Medusa 2.23.0 (core/framework) штатного rate limiting нет (подтверждено в 5.1); из инфраструктуры доступны зарегистрированные официальные модули: **Cache Module с провайдером cache-redis** (общий Redis; API `get(key)` / `set(key, data, ttlSeconds)` — TTL в секундах) и **Locking Module с провайдером locking-postgres** (advisory-локи, `execute(key, fn, {timeout})` — прием 4.5). Выбранный механизм: счетчики_attempts хранятся в Redis через Cache Module; инкремент «read→check→set» сериализуется транзакционным advisory-локом Locking Module по ключу корзины счетчика — **атомарно между процессами без новых зависимостей** (ioredis напрямую не добавляется — pnpm-строгий режим потребовал бы нового dependency и пересборки; собственный сервис rate limiting не создается — правило задачи). TTL обновляется при каждой попытке (**скользящее окно**: счетчик живет `window` секунд после последней попытки — нет «осиротевших» бессрочных ключей, блокировка всегда истекает сама; формально это не фиксированное окно — задокументировано). Ключи: `ratelimit:<маршрут>:ip:<ip>` и `ratelimit:<маршрут>:id:<hmac>`; идентификатор (email/actor) нормализуется (trim+lowercase для email) и **хешируется HMAC-SHA256 с JWT_SECRET** — открытых email, паролей и токенов в ключах Redis и логах нет. **IP**: Medusa выставляет `app.set("trust proxy", 1)` → `req.ip` берется из X-Forwarded-For, который клиент подделывает при прямом доступе; лимитер по умолчанию использует **адрес TCP-сокета** (`req.socket.remoteAddress`, не подделывается) и игнорирует XFF; флаг `AUTH_RATE_LIMIT_TRUST_PROXY` (по умолчанию `false`) разрешает production-конфигурацию с reverse proxy, который ПЕРЕЗАПИСЫВАЕТ X-Forwarded-For (требование задокументировано для этапа 10). Ограничения принятой схемы: (а) **fail-open** — при недоступности Redis/ошибке лимит пропускается (запрос не блокируется дольше 500 мс на buckets, warn в логи, без идентификаторов) — доступность авторизации приоритетнее идеального лимита, а деградация Redis уже означает деградацию платформы (сессии/события); (б) socket-IP за reverse proxy без trust-proxy — общий бак на весь магазин (поэтому до настройки прокси этапа 10 лимиты по IP считаются вторичными, основная защита — лимиты по идентификатору); (в) NAT: один IP разделяет лимиты многих пользователей (окна короткие — 60 с); (г) лимиты считают ВСЕ попытки (успешные тоже) — middleware не знает исхода. **429** с заголовком `Retry-After` (значение окна) и телом `{"type":"rate_limited","message":...}` — одинаково для существующих/несуществующих email (проверка до аутентификации, перечисление невозможно); бессрочных блокировок нет (TTL всегда истекает). Защищаемые маршруты (фактический состав 2.23): `POST /auth/customer/emailpass` (вход), `.../register`, `.../reset-password`, `.../update` (смена по reset-токену), `POST /store/orders/:id/transfer/request`. Дефолты (env, формат `<max>/<window_seconds>`): login IP 30/60, ID 5/900; register IP 30/60, ID 5/3600; reset IP 30/60, ID 3/3600; update IP 30/60 (ID нет — токен непрозрачен); transfer IP 30/60, ID 10/3600. Лимиты по IP короткоокнопые (анти-burst), по идентификатору — строгие антибрутфорсовые. Штатные настройки JWT/сессий аудитом подтверждены и не меняются: JWT 24 ч (`jwtExpiresIn`), session cookie `connect.sid` HttpOnly, **Secure+SameSite=lax автоматически при NODE_ENV=production/staging** (framework), TTL сессии 10 ч, store Redis, logout отзывает сессию, refresh — штатный `/auth/token/refresh`.

## Известные проблемы (актуальные)

- **`subtotal` корзины/заказа включает доставку** (`subtotal = item_subtotal + shipping_subtotal`, Medusa 2.23): при отображении «итога без доставки» использовать `item_subtotal` (задокументировано в docs/api.md).
- **Промоушены Admin API создаются в `draft`** и не применяются к корзинам (200 без скидки) — активация `status:"active"` обязательна; витрина/Admin должны учитывать статус.
- ~~**Два одновременных запроса complete одной корзины создают два заказа**~~ — **устранено этапом 4.5** (серверная сериализация: транзакционный advisory-лок PostgreSQL на весь запрос, middleware `backend/src/api/middlewares/cart-completion.ts` на штатном маршруте; регрессионный тест `Promise.allSettled` в `store-cart-checkout.spec.ts`). Остаточное поведение: лок живет, пока жив запрос (зависший обработчик = зависший запрос — ограничение `execute` 2.23.0, задокументировано в решении №35); при обновлении Medusa повторить конкурентный probe.
- **Тестовые заказы аудита 4.1 и тестов 4.3–4.5** (гостевые; аудита — display_id 1–3, тестов — по одному-четыре на каждый прогон набора/probe, на момент завершения 4.5 всего 32) остаются в dev-БД — API удаления заказов в Medusa нет. Тестовые промокоды удаляются самим набором (в БД их нет); резервирования инвентаря заказов тестовых прогонов удаляются набором/probe-ом автоматически, остаются только резервирования заказов аудита 4.1 (2×2 худи + 1 стикерпак). В production тестовые заказы не создаются (требование этапа 10, решение №34).
- Цены в индексе — минимальная цена варианта в валюте (региональные записи одной валюты и прайс-листы сведены к одной величине): фильтрация/сортировка корректна, точная рассчитанная цена — только через `/store/products` (задокументировано).
- Две физические версии индекса сосуществуют после атомарного переключения (`_v2`, `_v3`); активная определяется по `search_index.active_version` (источник истины модуля), окно 30 с после swap обслуживается предыдущей ПОЛНОЙ версией.
- Кириллица в query-параметрах должна быть percent-encoded (стандартное поведение браузеров/SDK; сырой curl без кодирования получает 400 от HTTP-слоя до приложения).
- Семантика `in_stock=false`: «есть отсутствующие варианты» (согласовано со счетчиком фасета) — задокументировано в docs/api.md.
- Значения характеристик синхронизируются с индексом автоматически по событиям модуля `catalog_attributes.product-attribute-value.*` (~1–2 с, этап 3.6.1). Удаления значений — soft delete: list-методы модуля и витрина видят только живые строки, но физические строки накапливаются с `deleted_at` (та же семантика, что у каскадов Medusa; очистка не реализована). Ручное изменение товара (`product.updated`) и `make search-reindex` по-прежнему работают как дополнительные пути синхронизации; сверка индекса (`make search-reconcile`, job `search-index-reconcile`) закрывает разрывы автоматически.
- Сверка индекса читает сырые документы Meilisearch master key-ом (`fetchDocuments`): Meilisearch запрещает изменять `actions` существующих API-ключей, поэтому право documents.get нельзя выдать провижинированным ключам без пересоздания их значений. Чтение — внутренняя серверная операция, ключ не покидает backend-контейнер.
- Сверка сравнивает документы канонической формой (сортировка ключей объектов и элементов массивов): порядок элементов массивов не входит в контракт поискового документа. Защита от параллельного запуска — Locking Module с провайдером locking-postgres (межпроцессные advisory-локи); при мультиинстансном развертывании достаточно общей БД приложения, отдельного сервиса не требуется.
- Событие `catalog_attributes.product-attribute-value.deleted` разрешается только через подписчик-мост (обогащение `product_id`): «сырое» событие, попавшее в consume напрямую, дает пустой резолвинг (трата одного query.graph-запроса) — задокументированное поведение, не ошибка.
- **Техдолг: флаг `searchable` характеристики** — хранится в БД, валидируется и редактируется Admin API, но не потребляется индексатором (все характеристики попадают в поисковый объект `attributes` независимо от флага). Зафиксировано по результатам архитектурного аудита (27.11.2026); решение отложено на этап 4+: либо учесть флаг в индексаторе, либо удалить поле (миграция). Функциональность не затронута.
- **Техдолг: проверка заполненности индекса в `make search-init`** не учитывает `MEILISEARCH_INDEX_PREFIX` (сравнивает имя корневого индекса `products` с физическими `store_products_vN`) — на заполненном каталоге скрипт выполняет холостую идемпотентную in_place переиндексацию вместо пропуска (найдено на приемке 3.8; операция безопасна и идемпотентна, результат корректен). Задокументировано в docs/indexing.md.
- **Производительность на больших каталогах не проверялась** (демо-каталог — 12 товаров/30 документов): архитектура фасетного поиска выполняет count-запрос на каждое значение каждого фасета (одним multi-search вызовом) — время ответа растет с числом значений фасетов; полная переиндексация и сверка батчевые (50 товаров/1000 документов на запрос), но нагрузочное тестирование — этап 10.
- **Конкурентные сценарии**: защита сверки от параллельного запуска и конкурентных изменений покрыта тестами 3.6.3; НЕ проверялись — конкурентная полная переиндексация из нескольких exec-процессов и multi-инстансное развертывание backend (механизмы — locking-postgres и BullMQ `concurrency: "forbid"` — штатные, но живых сценариев с несколькими инстансами в dev-окружении нет; вынесено на этап 10).
- **Резолвер активного индекса зависит от внутренней схемы Search Module** (таблицы `search_index`/`search_index_version`, публичного API активной версии у модуля нет): при изменении схемы модулем в следующих версиях Medusa требуется адаптация SQL-запроса (`resolveActivePhysicalNameFromModule`); деградация — последняя подтвержденная ready-версия/503.
- **Master key Meilisearch используется сверкой** для чтения сырых документов (`documents/fetch`): ограничение самого Meilisearch (`actions` существующих API-ключей иммутабельны) — право documents.get нельзя выдать провижинированному ключу без пересоздания его значения. Чтение — внутренняя серверная операция; ключ не покидает backend-контейнер (проверено тестами утечки, 3.6.3).

## Принятые решения этапа 2 (архитектурный журнал)

1. **Официальный Medusa JS SDK как транспорт** (`@medusajs/js-sdk@2.23.0`, версия = backend). Фасад вызывает публичный `sdk.client.fetch` с generics `HttpTypes` вместо сахарных методов `sdk.store.*`: typed-методы SDK не принимают `signal`/timeout, а требования этапа включают настраиваемый таймаут и отмену запросов. Фасад — «минимальная обертка»: base URL, publishable key, сериализация query и `FetchError` остаются на SDK.
2. **Таймаут/отмена на транспортном уровне**: каждый запрос получает `AbortSignal.timeout(timeoutMs)`; внешний `signal` объединяется через `AbortSignal.any` — отмена реальная, а не promise-race.
3. **Браузер → Medusa напрямую** (после hydration), SSR → внутренняя Docker-сеть. Стандартная схема storefront Medusa; исключает proxy-дублирование маршрутов; CORS уже настроен; publishable key и публичный URL не секреты.
4. **Регион по умолчанию без хардкода**: первый регион с валютой магазина (`STORE_CURRENCY`), иначе первый доступный — соответствует seed этапа 1 и масштабируется на мультирегиональность.
5. **`error` в `useStore` хранит сериализуемый снимок** `CommerceErrorData`, а не экземпляр Error — Error не сериализуется в Nuxt payload корректно.
6. **Авто-`fields` только для calculated_price** при переданном контексте ценообразования; все прочие query-параметры проходят из компонентов без магии (явность).
7. **Нормализация особенности Medusa 2.23**: `/store/product-categories/:id` возвращает 200 `{}` для несуществующей категории — клиент превращает это в честный 404 (`CommerceError`), инкапсулируя особенность от компонентов.
8. **Данные после hydration — из payload** (`useAsyncData` + `callOnce` + `useState`): повторных запросов нет (проверено в браузере по network).
9. **Пустых групп и заглушек нет**: cart/checkout/auth появятся вместе с соответствующими этапами; фабрика в `shared/` доступна и серверным Nitro-маршрутам, когда они понадобятся (cookies/сессии — этапы 6–7).
10. **Тесты**: unit — моки fetch только для логики самой обертки; контракт Medusa — исключительно интеграционные тесты на живом backend (`make test` в Docker с реальным publishable key).
