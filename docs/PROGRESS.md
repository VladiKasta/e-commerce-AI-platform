## Принятые решения этапа 3 (продолжение журнала)

11. **Официальный Search Module Medusa 2.23** вместо собственного Catalog Indexer: индексация/версионирование/ingestion/seeding — штатные механизмы; собственный код — только провайдер и определение индекса. Выбор соответствует правилу №1 AGENTS.md.
12. **Документ = вариант × валюта + distinct** — единственная модель, одновременно дающая вариант-совместную фильтрацию (критический сценарий) и точную пагинацию (прототип, 37/37).
13. **Точные счетчики уникальных товаров**: facetDistribution Meilisearch считает варианты → per-value count-запросы (multi-search, hitsPerPage=0, page-режим с точным totalHits).
14. **Динамические характеристики** фильтруются через родительский объект `attributes` в filterableAttributes Meilisearch (проверено прототипом): новые характеристики работают без изменения настроек индекса. Маршруты валидируют коды фильтров по реестру характеристик; валидатор полей Search Module для динамических путей не используется (обход задокументирован).
15. **В v2 сервисы создаются только в модулях** (официальная документация): `src/services` приложения не регистрируются. CatalogSearchService инстанцируется маршрутами напрямую с request scope.
16. **Доступ к Meilisearch из каталога** — через публичный конструктор собственного провайдера; активная версия индекса — из `search_index.active_version` официального Search Module (через публичный `PG_CONNECTION` Medusa). Публичного API активной версии у Search Module не существует — модели объявлены внутренней бухгалтерией модуля (`models: []` в joiner-конфиге). Эвристика максимального номера физической версии **полностью удалена**: индекс выбирается только по подтверждению из БД модуля; при ошибке служебного запроса — деградация к последней подтвержденной ready-версии, при её отсутствии — HTTP 503 `search_unavailable`. Переключение атомарно с точки зрения читателей: пока новая версия строится, active_version указывает на прежнюю ПОЛНУЮ версию (проверено мониторингом во время переиндексации: 14/14 запросов HTTP 200 total=12 до/во время/после swap).
17. **Admin API характеристик — только штатные механизмы Medusa 2.23**: маршруты в `src/api/admin/**` защищаются глобальным `authenticate("user")` для `/admin/*` (401 без Bearer JWT — проверено), валидация — zod-схемы (`@medusajs/framework/zod`) + `validateAndTransformBody/validateAndTransformQuery` (те же middleware, что у ядра), данные — сгенерированные CRUD-методы MedusaService модуля (`createAttributes`, `softDeleteAttributeOptions`, `setProductAttributeValues`, …) без дублирования бизнес-логики. Обновления в Admin API выполняются методом POST (конвенция ядра). Новые модели не создавались.
18. **Целостность при удалениях**: удаление характеристики — каскадный soft delete (значения товаров → допустимые значения → привязки → сама характеристика); удаление допустимого значения — вместе со ссылающимися значениями товара. Проверено SQL-запросом: после удаления тест-характеристики 0 живых строк во всех 4 таблицах модуля. Неизменяемые ключи: `code`/`data_type` характеристики и `value` опции — на них ссылается поисковый индекс (ключ `attributes.<code>`) и типизированные колонки значений.
19. **События модуля и индекс (проверено фактом, 26.11.2026)**: Medusa 2.23 излучает для модуля только события `catalog_attributes.attribute.*` (в event bus за проверку: 7 created — 6 seed + 1 через Admin API, 1 updated); события моделей `product_attribute_value`/`attribute_option`/`category_attribute` **не излучаются** (0 событий при 51 seed-значении и записях Admin API); `attribute.updated` переиндексацию не запустил. Изменения характеристик попадают в индекс при пересборке документа затронутого товара (события товара, ~40–60 с, проверено) или полной переиндексации (`make search-reindex`). Разрыв закроет «job сверки индекса» (остаток этапа 3); поиск и индексация в этой задаче не изменялись (ограничение этапа).
20. **Оптимизация фасетного поиска (27.11.2026, эмпирически)**: facetDistribution Meilisearch при distinct считает **представителей** distinct-дедупликации (по одному документу на товар: у худи с 5 размерами distribution = {L:1}; точный count-запрос size=S дает 6 товаров против 2 в distribution) — счетчики distribution не являются ни вариантами, ни точными счетчиками уникальных товаров, поэтому per-value count-запросы сохранены. Из этого следуют два правила оптимизации: (а) для фасета без активного собственного фильтра disjunctive-режим совпадает с базовым запросом → distribution/stats запрашиваются в базовом запросе, отдельный подзапрос — только активным фасетам; (б) **пустая** distribution (Meilisearch возвращает `{}`) = подтвержденный ноль для всех значений фасета → count-запросы не нужны (в модели данных этой задачи значения фасета присутствуют на всех документах товара с этой опцией, поэтому пустая distribution означает отсутствие значений у всех подходящих документов); отсутствие значения в **непустой** distribution нулем не является (maxValuesPerFacet=100). Кэширование не вводилось, модели/индексы/зависимости не менялись.

Реализация не начата; текущая задача разработки (остаток этапа 3) не изменена.
23. **Синхронизация характеристик: реальные имена событий и мост для удалений (этап 3.6.1, проверено фактом 27.11.2026)**. Уточнение решения №19: Medusa 2.23 **излучает** события всех моделей модуля, но строит имена через `buildModuleResourceEventName` = `kebabCase(имя модели)`: модель `product_attribute_value` эмитируется как `catalog_attributes.product-attribute-value.*` (однословная `attribute` совпадает с snake-формой, поэтому её события работали и раньше). Объявленные в определении индекса snake-имена не совпадали с эмитируемыми kebab-именами — шина событий отбрасывала их молча (нет подписчиков → нет доставки). Определение индекса переведено на фактические имена. Событие `deleted` несет только `data={id}` строк, которые к моменту доставки недоступны: значения удаляются soft delete-ом (все пути приведены к семантике каскадов модуля), а подписчик `catalog-attribute-values-search` резолвит товары через сервис модуля (`withDeleted: true`) и подает обогащенное событие в `searchModule.ingest()` — официальный вход ingestion-конвейера (тот же, что у встроенного подписчика search-ingestion). Второй индексатор не создавался: документы собирает то же определение индекса; полная переиндексация для одиночных изменений не используется (замер сквозным сценарием: ~1 с).
24. **Сверка индекса — только штатные механизмы Medusa 2.23 (этап 3.6.2, проверено фактом 27.11.2026)**. Аудит Search Module показал готовые механизмы: (а) `reindex({index, filters})` — официальная частичная переиндексация «in-place» в активную версию, никогда не swap-ит, берет lock `search:seed:*`, передает `filters` в seed определения (наш seed поддерживал `product_ids` с этапа 3.2); (б) `deleteDocuments({index, filters})` с быстрым путем удаления по первичному ключу `{id: [...]}`; (в) Scheduled Jobs (workflow engine, BullMQ repeatable с `concurrency: "forbid"`); (г) Locking Module с официальным провайдером `locking-postgres` (advisory-локи в БД приложения, работают между процессами/инстансами). Сверка (`backend/src/jobs/search-index-reconcile.ts`) только композирует их: ожидаемые документы собирают экспортированные загрузчики того же определения индекса, ремонт — через официальный API модуля; чтение сырых документов — метод `fetchDocuments` клиента провайдера (POST documents/fetch, без distinct-дедупликации). Мастер-ключ для чтения: Meilisearch иммутабелен в `actions` существующих API-ключей (PATCH /keys принимает только description/name — эмпирически поймано в первой попытке, из-за чего boot-seeding падал до отката), право documents.get нельзя добавить провижинированным ключам без пересоздания значения — чтение идет master key-ом, серверная внутренняя операция. Каноническое сравнение документов сортирует ключи объектов и элементы массивов: массивы документа (category_ids, значения характеристик) Meilisearch трактует как множества, порядок не входит в контракт и не должен порождать ложные «устаревшие» документы и холостые переиндексации. Дефолтный in-memory Locking Module не защищает между процессами (выявлено живым тестом параллельного запуска) — зарегистрирован locking-postgres, что заодно сделало межпроцессными seed-локи Search Module (защита reindex↔полная переиндексация `make search-reindex` из exec-процесса). Расписание по умолчанию раз в час — сверка дешевая (батчи, только чтения), полная переиндексация по расписанию не выполняется; частота настраивается `SEARCH_RECONCILE_CRON` без изменения кода.
25. **Реентерабельность Locking Module по ownerId (найдено тестами этапа 3.6.3, 27.11.2026)**. Провайдеры Locking Module (in-memory и locking-postgres) считают запрос с ownerId, совпадающим с владельцем удерживаемого lock-а, реентерабельным и пропускают его acquire без конфликта (advisory-lock: `row.owner_id !== ownerId` — единственная проверка). Константный ownerId в `executeSearchReconcile` («search-reconcile-job») пускал параллельные запуски сверки одного владельца мимо lock-а — два одновременных POST /admin/search/reconcile выполняли полный ремонт оба. Исправлено уникальным per-run ownerId (`search-reconcile-<uuid>`) — это же штатная рекомендация документации Locking Module («acquire the lock with an owner that is unique to this call», иначе release может снять чужой lock). Вывод для всех будущих использованием locking в проекте: ownerId — идентификатор ВЫЗОВА, а не сервиса. Защита scheduled job от наложения не зависела от дефекта (BullMQ `concurrency: "forbid"`), ремонт идемпотентен — фактических повреждений дефект не создавал, только лишние параллельные исполнения.

## Известные проблемы (актуальные)

- Цены в индексе — минимальная цена варианта в валюте (региональные записи одной валюты и прайс-листы сведены к одной величине): фильтрация/сортировка корректна, точная рассчитанная цена — только через `/store/products` (задокументировано).
- Две физические версии индекса сосуществуют после атомарного переключения (`_v2`, `_v3`); активная определяется по `search_index.active_version` (источник истины модуля), окно 30 с после swap обслуживается предыдущей ПОЛНОЙ версией.
- Кириллица в query-параметрах должна быть percent-encoded (стандартное поведение браузеров/SDK; сырой curl без кодирования получает 400 от HTTP-слоя до приложения).
- Семантика `in_stock=false`: «есть отсутствующие варианты» (согласовано со счетчиком фасета) — задокументировано в docs/api.md.
- Значения характеристик синхронизируются с индексом автоматически по событиям модуля `catalog_attributes.product-attribute-value.*` (~1–2 с, этап 3.6.1). Удаления значений — soft delete: list-методы модуля и витрина видят только живые строки, но физические строки накапливаются с `deleted_at` (та же семантика, что у каскадов Medusa; очистка не реализована). Ручное изменение товара (`product.updated`) и `make search-reindex` по-прежнему работают как дополнительные пути синхронизации; сверка индекса (`make search-reconcile`, job `search-index-reconcile`) закрывает разрывы автоматически.
- Сверка индекса читает сырые документы Meilisearch master key-ом (`fetchDocuments`): Meilisearch запрещает изменять `actions` существующих API-ключей, поэтому право documents.get нельзя выдать провижинированным ключам без пересоздания их значений. Чтение — внутренняя серверная операция, ключ не покидает backend-контейнер.
- Сверка сравнивает документы канонической формой (сортировка ключей объектов и элементов массивов): порядок элементов массивов не входит в контракт поискового документа. Защита от параллельного запуска — Locking Module с провайдером locking-postgres (межпроцессные advisory-локи); при мультиинстансном развертывании достаточно общей БД приложения, отдельного сервиса не требуется.
- Событие `catalog_attributes.product-attribute-value.deleted` разрешается только через подписчик-мост (обогащение `product_id`): «сырое» событие, попавшее в consume напрямую, дает пустой резолвинг (трата одного query.graph-запроса) — задокументированное поведение, не ошибка.
- **Техдолг: флаг `searchable` характеристики** — хранится в БД, валидируется и редактируется Admin API, но не потребляется индексатором (все характеристики попадают в поисковый объект `attributes` независимо от флага). Зафиксировано по результатам архитектурного аудита (27.11.2026); решение отложено на этап 4+: либо учесть флаг в индексаторе, либо удалить поле (миграция). Функциональность не затронута.
- **Техдолг: проверка заполненности индекса в `make search-init`** не учитывает `MEILISEARCH_INDEX_PREFIX` (сравнивает имя корневого индекса `products` с физическими `store_products_vN`) — на заполненном каталоге скрипт выполняет холостую идемпотентную in_place переиндексацию вместо пропуска (найдено на приемке 3.8; операция безопасна и идемпотентна, результат корректен). Задокументировано в docs/indexing.md.
- **Производительность на больших каталогах не проверялась** (демо-каталог — 12 товаров/30 документов): архитектура фасетного поиска выполняет count-запрос на каждое значение каждого фасета (одним multi-search вызовом) — время ответа растет с числом значений фасетов; полная переиндексация и сверка батчевые (50 товаров/1000 документов на запрос), но нагрузочное тестирование — этап 10.
- **Конкурентные сценарии**: защита сверки от параллельного запуска и конкурентных изменений покрыта тестами 3.6.3; НЕ проверялись — конкурентная полная переиндексация из нескольких exec-процессов и multi-инстансное развертывание backend (механизмы — locking-postgres и BullMQ `concurrency: "forbid"` — штатные, но живых сценариев с несколькими инстансами в dev-окружении нет; вынесено на этап 10).
- **Резолвер активного индекса зависит от внутренней схемы Search Module** (таблицы `search_index`/`search_index_version`, публичного API активной версии у модуля нет): при изменении схемы модулем в следующих версиях Medusa требуется адаптация SQL-запроса (`resolveActivePhysicalNameFromModule`); деградация — последняя подтвержденная ready-версия/503.
- **Master key Meilisearch используется сверкой** для чтения сырых документов (`documents/fetch`): ограничение самого Meilisearch (`actions` существующих API-ключей иммутабельны) — право documents.get нельзя выдать провижинированному ключу без пересоздания его значения. Чтение — внутренняя серверная операция; ключ не покидает backend-контейнер (проверено тестами утечки, 3.6.3).

## Принятые решения этапа 2 (архитектурный журнал)

1. **Официальный Medusa JS SDK как транспорт** (`@medusajs/js-sdk@2.23.0`, версия = backend). Фасад вызывает публичный `sdk.client.fetch` с generics `HttpTypes` вместо сахарных методов `sdk.store.*`: typed-методы SDK не принимают `signal`/timeout, а требования этапа включают настраиваемый таймаут и отмену запросов. Фасад — «минимальная обертка»: base URL, publishable key, сериализация query и `FetchError` остаются на SDK.
2. **Таймаут/отмена на транспортном уровне**: каждый запрос получает `AbortSignal.timeout(timeoutMs)`; внешний `signal` объединяется через `AbortSignal.any` — отмена реальная, а не promise-race.
3. **Браузер → Medusa напрямую** (после hydration), SSR → внутренняя Docker-сеть. Стандартная схема storefront Medusa; исключает proxy-дублирование маршрутов; CORS уже настроен; publishable key и публичный URL не секреты.
4. **Регион по умолчанию без хардкода**: первый регион с валютой магазина (`STORE_CURRENCY`), иначе первый доступный — соответствует seed этапа 1 и масштабируется на мультирегиональность.
5. **`error` в `useStore` хранит сериализуемый снимок** `CommerceErrorData`, а не экземпляр Error — Error не сериализуется в Nuxt payload корректно.
6. **Авто-`fields` только для calculated_price** при переданном контексте ценообразования; все прочие query-параметры проходят из компонентов без магии (явность).
7. **Нормализация особенности Medusa 2.23**: `/store/product-categories/:id` возвращает 200 `{}` для несуществующей категории — клиент превращает это в честный 404 (`CommerceError`), инкапсулируя особенность от компонентов.
8. **Данные после hydration — из payload** (`useAsyncData` + `callOnce` + `useState`): повторных запросов нет (проверено в браузере по network).
9. **Пустых групп и заглушек нет**: cart/checkout/auth появятся вместе с соответствующими этапами; фабрика в `shared/` доступна и серверным Nitro-маршрутам, когда они понадобятся (cookies/сессии — этапы 6–7).
10. **Тесты**: unit — моки fetch только для логики самой обертки; контракт Medusa — исключительно интеграционные тесты на живом backend (`make test` в Docker с реальным publishable key).

## Известные проблемы (актуальные)

- `medusa develop` в контейнере логирует предупреждение vite о deprecated-формате `server.hmr.*` (vite 8) — не влияет на работу (унаследовано с этапа 1).
- Демо-изображения товаров хостятся в публичном S3 Medusa — при отсутствии интернета картинки не загрузятся (товары и цены работают) (унаследовано).
- `pnpm peers check` показывает предупреждения по eslint-плагинам из цепочки `@nuxt/eslint` (eslint 9.x против unicorn>=10) — существовало до этапа 2, не влияет на lint.
- Production-сборка в dev-контейнере невозможна из-за anon-volume на `.output` (см. ограничение выше); для проверки сборки этапа 2 использован одноразовый контейнер.
