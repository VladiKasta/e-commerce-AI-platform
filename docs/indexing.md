## Структура поисковых документов

Индекс `products` (физические версии `store_products_vN`, префикс — `MEILISEARCH_INDEX_PREFIX`). **Один документ = вариант товара × валюта**; `id` документа — `` `${variant_id}__${currency_code}` `` (например, `variant_01M87JXH78C4ESGHPEMMCBHZWA__rub`). На демо-каталоге: 12 товаров / 28 вариантов / 30 документов.

Схема (`defineSearchIndex` в `backend/src/search/products.ts`):

| Поле | Тип | Флаги | Источник |
|---|---|---|---|
| `id` | keyword | primary key | `variant_id__currency` |
| `product_id` | keyword | filterable | товар |
| `variant_id` | keyword | — | вариант |
| `status` | keyword | filterable | статус товара (в индекс попадают только `published`) |
| `title` | text | searchable, sortable | название товара |
| `description` | text | searchable | описание |
| `sku` | text | searchable, filterable | артикул варианта |
| `handle` | keyword | — | slug товара |
| `thumbnail` | keyword | — | миниатюра |
| `currency_code` | keyword | filterable | валюта записи цены |
| `price` | float | filterable, sortable, facetable (range/stats) | минимальная цена варианта в валюте |
| `in_stock` | boolean | filterable, facetable | наличие варианта |
| `category_ids` / `category_handles` | keyword[] | filterable | категории товара |
| `collection_ids` / `collection_handles` | keyword[] | filterable | коллекция |
| `sales_channel_ids` | keyword[] | filterable | каналы продаж товара |
| `attributes` | object | filterable (родитель покрывает все подполя) | характеристики: уровень товара + вариант-специфичные |
| `created_at` / `updated_at` | integer (unix) | sortable | таймстемпы товара |

`attributes` — динамический объект: ключ = `code` характеристики, значение = скаляр (единственное значение) или массив (multi_select/несколько значений). Пример документа худи «Полярное»: `"attributes": {"brand": "north-polar", "material": ["polyester", "cotton"], "rating": 4.7, "eco": true, "size": "L"}`.

Сборщики `loadProductRows` / `loadProductAttributeData` / трансформация `buildProductDocuments` экспортированы из определения индекса и переиспользуются сверкой (второго индексатора нет).

## Учет вариантов, валют, цен и наличия

**Варианты.** Каждый документ принадлежит одному варианту: значения, определенные покупаемым вариантом (`option_title`-характеристики: цвет/размер; ручные вариант-специфичные значения), попадают **только в документы этого варианта**. Это дает вариант-ориентированную фильтрацию: комбинация «Чёрный + M + в наличии» находится по одному документу, а не по разным вариантам товара.

**Валюты.** Валюта — атрибут документа; маршруты каталога всегда фильтруют по `currency_code` региона (регион проверяется через модуль Region). Вариант без цен в какой-либо валюте не создает документ в ней.

**Цены.** Для каждой валюты варианта берется **минимальная** цена; записи прайс-листов (`price_list_id`) **исключаются** (приватные цены не входят в поисковую проекцию). Суммы — в основных единицах Medusa (1490 = 1490 ₽). Точная рассчитанная цена для карточки товара — только через `/store/products` (ограничение задокументировано).

**Наличие.** `in_stock = manage_inventory === false || allow_backorder === true || (Σ stocked_quantity − Σ reserved_quantity) > 0` — по складам inventory-уровня варианта.

**Фильтрация состава:** в индекс попадают только товары `status = "published"` и связанные с каналами продаж (базовый фильтр запросов добавляет `sales_channel_ids` канала publishable key).

## События Medusa и их payload

Определение индекса подписано на **фактически эмитируемые** Medusa 2.23 события (полный список — поле `events` определения). События несут минимум данных: обычно `data = { id: string | string[] }` — id затронутой сущности; consume резолвит их до товаров через `query.graph`.

| Группа событий | Примеры | Payload | Резолвинг до товаров |
|---|---|---|---|
| Товар | `product.product.created/updated/deleted/attached/detached` | `{id: prod_...}` или `{product_id}` для attached/detached | напрямую; отсутствующие id → delete документов |
| Вариант | `product.product-variant.created/updated/deleted` | `{id: variant_...}` | вариант → `product_id` |
| Категория/коллекция | `product.product-category.updated`, `product.product-collection.updated` | `{id}` | обратный поиск товаров по category/collection |
| Цены | `pricing.price.created/updated/deleted` | `{id: price_...}` | цена → price_set → link → вариант → товар |
| Инвентарь | `inventory.inventory-item.*`, `inventory.inventory-level.*`, `inventory.reservation-item.*` | `{id}` | item/level/reservation → вариант → товар |
| Характеристики | `catalog_attributes.attribute.created/updated/deleted` | `{id: attr_...}` | значения по attribute_id → товары, у которых есть значения |
| Значения характеристик | `catalog_attributes.product-attribute-value.created/updated/deleted` | `{id: prodattr_...}` | значение → `product_id` (см. ниже) |

Два критичных нюанса Medusa 2.23 (проверено на живом окружении, журнал решений №19/23):

1. **Имена событий моделей модуля — kebab-case**: `buildModuleResourceEventName` строит имя из `kebabCase(имени модели)` — модель `product_attribute_value` эмитируется как `catalog_attributes.product-attribute-value.*`. Snake-вариант не совпадал с эмитируемыми именами и молча отбрасывался шиной.
2. **Событие `deleted` значений характеристик** несет только `{id}` строк, которые к моменту доставки уже soft-deleted и недоступны remote query. Подписчик `backend/src/subscribers/catalog-attribute-values-search.ts` (мост) резолвит затронутые товары через сервис модуля (`listProductAttributeValues` с `withDeleted: true`) и повторно подает обогащенное событие (`data.product_id`) в официальный ingestion-конвейер `searchModule.ingest()` — тот же вход, что у встроенного подписчика search-ingestion. «Сырое» событие, дошедшее в consume напрямую, дает пустой резолвинг (задокументированное поведение, не ошибка).

## Инкрементальная индексация

По умолчанию индекс обновляется **событийно** через официальный ingestion-конвейер Search Module:

```text
событие → searchModule.ingest → consume определения индекса
  → resolveAffectedProducts (query.graph)
  → upsertProducts: перечитать товары/варианты/цены/остатки/характеристики из PG
  → мутации: upsert пересобранных документов + delete для исчезнувших/снятых с публикации
```

Свойства (проверены замерами):

- **обновляются только затронутые товары** — полной переиндексации не происходит;
- **значения характеристик** появляются в поиске через ~1–2 с после Admin API (замер сквозного сценария: назначение/изменение/удаление — 1,0 с);
- события товара (`product.updated`) обрабатываются асинхронно шиной Redis — фактическое обновление документа ~40–70 с; Medusa излучает `product.updated` только при реальном изменении;
- идемпотентность: повторные события пересобирают те же документы (upsert);
- `upsertProducts` удаляет документы товаров, которых больше нет в PG или которые сняты с публикации (`action: "delete"` с фильтром `product_id`).

## Активные версии индекса

Search Module хранит версии физического индекса в собственных таблицах: `search_index` (корневое имя, `active_version`, `deleted_at`), `search_index_version` (`version`, `physical_name`, `status` — `building`/`ready`).

- **Активная версия выбирается только по подтверждению из БД модуля** (SQL-резолвер `resolveActivePhysicalNameFromModule`, см. [ARCHITECTURE.md](ARCHITECTURE.md)): join `search_index` × `search_index_version` по `active_version` с условиями `status='ready'`, `deleted_at IS NULL`. Публичного API активной версии у модуля нет (модели объявлены внутренней бухгалтерией); резолвер зависит от этой внутренней схемы — при изменении её в следующих версиях Medusa потребуется адаптация (зафиксировано как ограничение).
- **TTL-кэш 30 с** в каталог-сервисе ускоряет запросы; эвристика максимального номера версии исключена — строящаяся версия существует до активации и не должна читаться.
- **Деградация**: при ошибке служебного SQL сервис обслуживает запросы из последней подтвержденной ready-версии (она была атомарно активирована ранее); если подтвержденной версии нет — HTTP 503 `search_unavailable`.
- **Атомарность для читателей**: пока новая версия строится, `active_version` указывает на прежнюю ПОЛНУЮ версию. Проверено мониторингом во время переиндексации: все запросы до/во время/после swap — HTTP 200 со стабильной выдачей.
- После swap старые физические версии остаются в Meilisearch (очищает сам модуль); фактическое состояние выводит `make search-status`.

## Полная переиндексация

```bash
make search-reindex   # стратегия swap: новая версия + атомарное переключение
```

- Строится **новая** физическая версия (`store_products_vN+1`), заполняется полным проходом seed-генератора (батчи по 50 товаров, курсор по `id`, возобновление по `last_key`, catch-up-проход изменений с момента старта), затем атомарно активируется.
- Читатели все это время обслуживаются прежней версией; операция синхронная — выход из скрипта означает завершенную замену (провайдер ждет задач Meilisearch).
- Идемпотентна: повторный запуск строит следующую версию поверх актуальной (лишних документов не создает; upsert-ы).
- **Когда нужна**: массовые операции (изменение схемы документа, настроек индекса — `MEILISEARCH_SYNONYMS`/`STOP_WORDS`, глобальные изменения каталога). Для одиночных изменений не используется.

Первоначальная индексация пустого индекса — `make search-init` (вызывается и при `make init`): план миграций (создает отсутствующие физические индексы, применяет настройки) + заполнение пустых индексов `reindex in_place`. Известная особенность: проверка «индекс уже заполнен» сравнивает имя корневого индекса с физическими (`store_...`) без учета префикса `MEILISEARCH_INDEX_PREFIX`, поэтому на заполненном каталоге `make search-init` выполняет холостую идемпотентную переиндексацию in_place (результат корректен, операция безопасна; техдолг — [PROGRESS.md](PROGRESS.md)).

## Периодическая сверка и восстановление

Scheduled job **`search-index-reconcile`** (`backend/src/jobs/search-index-reconcile.ts`): расписание `SEARCH_RECONCILE_CRON` (по умолчанию `0 * * * *` — раз в час), BullMQ repeatable с `concurrency: "forbid"`; ручной запуск — `make search-reconcile` или `POST /admin/search/reconcile` (маршрут №27 [api.md](api.md), возвращает ту же сводку).

Алгоритм (PostgreSQL — источник истины):

1. **Проход 1**: батчи товаров по 50 из PG (id-курсор, каталог не грузится в память); для каждого товара собираются **ожидаемые** документы теми же загрузчиками и трансформацией, что у индексатора (`buildProductDocuments` — второго индексатора нет); фактические документы читаются из активного физического индекса (`POST /indexes/{uid}/documents/fetch`, master key-ом); сравнение — каноническая форма (сортировка ключей объектов и элементов массивов: порядок элементов массивов не входит в контракт документа).
2. **Проход 2**: все `product_id` индекса против PG — **сироты** (документы товаров, отсутствующих в PG, включая неопубликованные).
3. **Ремонт — только затронутых товаров, штатными механизмами модуля**: отсутствующие/устаревшие → `reindex({index, filters: {product_ids}})` (официальная частичная переиндексация in-place в активную версию, без swap); лишние → `deleteDocuments({filters: {id}})`; сироты → `deleteDocuments({filters: {product_id}})`.

Сводка (лог + ответ маршрута №27):

```json
{
  "status": "completed",
  "summary": {
    "physicalName": "store_products_v3",
    "checkedProducts": 12, "checkedDocs": 30,
    "missing": 0, "stale": 0, "extra": 0,
    "orphanProducts": 0, "orphanDocs": 0,
    "reindexedProducts": 0, "deletedDocs": 0, "errors": 0
  }
}
```

Свойства (все проверены интеграционными тестами и живыми инъекциями повреждений): идемпотентность (повтор на корректном индексе — 0 записей), обнаружение/ремонт 4 типов повреждений (отсутствующий, испорченный, лишний, сирота) и полной потери индекса, недоступность Meilisearch — warn без записей и падения приложения, конкурентные изменения во время сверки сходятся (финальная сверка — 0 расхождений).

## Межпроцессные блокировки

Штатный **Locking Module** с официальным провайдером `locking-postgres` (advisory-локи в таблице `locking` БД приложения — работают между процессами и инстансами; отдельный сервис не нужен):

| Lock | Владелец | Что защищает |
|---|---|---|
| `search:seed:products` | Search Module (внутренний) | seeding/переиндексацию: частичная (`reindex`) и полная (`swap`) ждут/конфликтуют корректно |
| `search:reconcile:products` | job сверки | параллельные запуски сверки (расписание × ручной запуск × маршрут №27): второй запуск — `"status": "skipped"` |

`ownerId` сверки — уникальный на каждый запуск (`search-reconcile-<uuid>`): провайдеры Locking Module считают одинакового владельца реентерабельным (дефект с константным ownerId найден тестами 3.6.3 и исправлен; вывод: ownerId — идентификатор вызова, не сервиса). Срок жизни lock-а — 30 минут (страховка от зависшего запуска).

## Команды управления индексом

| Команда | Действие | Идемпотентность |
|---|---|---|
| `make search-init` | План миграций индексов (создание + настройки) + первоначальная индексация пустых индексов | Да (на заполненном каталоге — холостая in_place переиндексация, см. выше) |
| `make search-reindex` | Полная переиндексация: новая версия + атомарный swap | Да (каждый запуск — новая версия) |
| `make search-status` | Здоровье Meilisearch, корневой индекс (status, полей), все физические версии с числом документов, проба поиска | Да |
| `make search-reconcile` | Одна сверка с ремонтом (та же логика, что job и маршрут №27) | Да (0 записей на корректном индексе) |
| `make search-logs` | Логи контейнера meilisearch | — |

Административный HTTP-маршрут: `POST /admin/search/reconcile` (Bearer JWT; параллельный запуск — `"status":"skipped"`).

## Диагностика и восстановление после сбоев

**Статус и состав индекса** (`make search-status`, фактический вывод на живом окружении):

```text
Meilisearch: OK (доступен)
Индекс «products»: provider=meilisearch, status=ready, полей=19
Физический индекс «store_products_v3»: документов=30
Физический индекс «store_products_v4»: документов=30
Проверка поиска: count=12, hits=1
```

**Настройки живого индекса** (внутри Docker-сети, из backend-контейнера; master key не покидает контейнер):

```bash
docker compose exec -T medusa wget -qO- \
  "http://meilisearch:7700/indexes/store_products_v4/settings" \
  --header "Authorization: Bearer $MEILISEARCH_MASTER_KEY"
```

**Симптомы и действия:**

| Симптом | Причина | Действие |
|---|---|---|
| Store API: HTTP 503 `search_unavailable` | Meilisearch недоступен / нет подтвержденной ready-версии | Проверить `make status`, `make search-logs`; после старта Meilisearch данные восстановятся сверкой (job по расписанию) |
| `make search-status`: индекс `status != ready` | Прерванное построение версии | Перезапуск medusa (boot-seeding достроит/починит версии) либо `make search-reindex` (новая версия + swap) |
| Лог сверки: `отсутствующих N / устаревших N / лишних N / сирот N > 0` | Рассинхронизация (потерянные события, ручные изменения) | Сверка ремонтирует сама; принудительно — `make search-reconcile` |
| Поиск не видит свежие значения характеристик | Потерянное событие | `make search-reconcile` (точечно) или любое `product.updated` затронутого товара |
| Массовые изменения/смена настроек (`MEILISEARCH_SYNONYMS`/`STOP_WORDS`) | Настройки применяются при создании версии | `make search-reindex` |
| `Meilisearch недоступен — сверка пропущена` в логах | Остановка meilisearch на момент job | Без записей; следующий запуск по cron отработает |
| Полная потеря индекса (документов 0) | Сброс volume/повреждение | `make search-reindex` (или `search-init` на пустом индексе); проверено — восстановление целиком |

**Восстановление после сбоя Meilisearch** проверено живой инъекцией: сверка обнаруживает и восстанавливает удаленные/испорченные/лишние документы и сироты в точности (id-множество + содержимое); полная потеря всех документов восстанавливается целиком за один запуск.

**Чувствительные данные**: чтение сырых документов сверкой выполняется master key-ом Meilisearch (`documents/fetch`) — Meilisearch запрещает изменять `actions` существующих API-ключей, поэтому право `documents.get` нельзя выдать провижинированным ключам без пересоздания их значений. Операция внутренняя, серверная; ключ не попадает в ответы Store API и исходники витрины (проверено тестами утечки). Поисковые запросы витрины выполняются отдельным ключом только с правами search, индексация — ключом только с правами записи (провижинируются провайдером из master key при старте).
